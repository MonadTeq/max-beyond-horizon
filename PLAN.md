# PLAN.md — Rust-клиент M.A.X. под Horizon (целевой план)

Версия: 6.0 · 2026-11-14
История: v1 — P2P-арбитр; v2 — клиент-сервер на C++; v3 — RE + Rust (постановка);
v4 — детальный план, ориентированный на RE; v5 — целевой план (C++-порт как оракул).
**v6 — архитектурное решение: клиент — полноценный lockstep-участник с
детерминированной симуляцией в max_core; протоколы бинарные (gRPC для Horizon,
UDP/ENet-семантика для игровой сессии); max_core переписывается идиоматичным Rust.**

## 0. Цели

1. **Цель 1 — Спецификации**: извлечь из C++-порта (основной источник) и оригинала
   (верификация) ровно то знание, которое нужно клиенту: модель состояния, форматы
   ресурсов, контракт протокола.
2. **Цель 2 — Rust-клиент**: модульный клиент (core/net/assets/render/app) —
   полноценный lockstep-участник: детерминированная симуляция в `max_core`,
   бинарные протоколы в `max_net`, сессия через Horizon.
3. **Цель 3 — Интеграция и эксплуатация**: Horizon-контракт (gRPC), CI,
   документация; реконнект/спектатор — по мере зрелости.

### Принцип источников (из v5)
- **`max-cpp-port/` — оракул №1 (неизменяемый)**: имена, структуры, константы,
  загрузчики форматов, сетевой слой. `src/` — наша развилка (headless-сервер,
  см. docs/src-fork.md).
- **`max-port-site/` — оракул №2**: save.md (формат V70), documentation.md
  (Watcom-конструкции), network.md, scripting.md.
- **RE оригинала (`max-original-dasm/`) — верификация и пробелы**.
- Ничего не реверсим «на будущее»: каждый RE-артефакт привязан к потребности.

## 1. Целевая картина

Готовый продукт: Rust-клиент M.A.X., который исполняет **полную детерминированную
симуляцию** (как равноправный lockstep-участник рядом с C++-клиентами/headless),
входит в сессию через Horizon (gRPC-лобби, бинарный тикет), играет партию 10+
ходов без расхождений (CRC-барьеры), рендерит мир из собственного состояния.
Все игровые данные — из оригинальных ресурсов (PATCHES.RES и др.).

### Архитектурные решения (v6)
1. **Lockstep, вариант 1**: клиент сам симулирует игру; сервер/headless —
   реле и арбитр барьеров, а не источник снапшотов (в коде C++ снапшотов нет:
   есть CRC-синхронизация юнитов, пакет 54, и аудит 23/24/49 — см. docs/protocol.md §8–9).
2. **Бинарные протоколы**:
   - Horizon (лобби/админ): **gRPC + protobuf** (схемы в `max-horizon-server/proto/`,
     единственный источник истины; клиенты Rust/C++ генерируются из .proto).
   - Игровая сессия: **UDP с каналами в семантике ENet** (ordered reliable), пакеты —
     плоские LE-структуры с полем версии (быстро, zero-copy; раскладки уже в
     docs/protocol.md). gRPC поверх TCP на сессию НЕ берём: head-of-line blocking
     вредит lockstep-барьерам.
3. **max_core переписывается**: полная симуляция (GameManager/UnitsManager/
   TaskManager/AI/пути) идиоматичным Rust — enum вместо magic-чисел, Option/Result
   вместо null, newtype-идентификаторы, итераторы, владение вместо ручных указателей.
4. **Детерминизм — жёсткое требование**: целочисленная арифметика как в C++ (без
   float в симуляции), фиксированный порядок итераций, RNG портируется 1:1
   (seed из `rng_seed`). Смешанная сессия C++/Rust требует бит-в-бит совпадения;
   до его подтверждения тестируем однородные сессии (только Rust).

## 3. Цель 1 — Спецификации

Порядок работы: взять из C++-порта → оформить в `docs/` или `formats/` → сверить с
байтами оригинала (где нужно) → пометить «проверено RE».

### 1.1 Модель состояния → `docs/state-model.md` + `max-original-dasm/structures.md`
- Источник №1: **`max-port-site/save.md`** — авторская спецификация формата V70
  (SaveFormatHeader, TeamInfo, TeamUnits/UnitValues/Complex, GameManagerState,
  UnitType ×93, условия победы/поражения по миссиям, битфилды карты ресурсов,
  unit hash ID). Источник №2: заголовки C++ (`src/*.h`, свериться с
  `max-cpp-port/`). RE-верификация — по потребности (1.4).
- Задача: перенести спецификацию в state-model.md (адаптировать под снапшоты
  headless-сервера: что входит, как кодируется).
- **Критерий**: по state-model.md можно написать `max_core` без чтения C++.

### 1.2 Форматы ресурсов → `max-original-dasm/formats/<format>.md`
- Источник: загрузчики C++ (`resource_manager.cpp` и пр.) + байты из `max-original/`.
- Приоритет: **RES/PATCHES** (контейнер, всё остальное через него) → карты
  (WRL/SCE/MPS) → спрайты (SPW) → анимации (FLC) → шрифты (FON) → звук/ролики (MSC/MVE).
- **Критерий**: по каждому документу Flash-агент пишет парсер в `max_assets` без
  обращения к C++-коду; RES дополнительно имеет эталонный Python-парсер.

### 1.3 Протоколы → `docs/protocol.md` + `.proto`-схемы ✅ (основа)
- Сделано: полный контракт (~70 сообщений: WS-лобби Horizon + UDP-сессия ENet,
  хендшейк/барьеры/приказы/чат; раскладки побайтово; открытые вопросы в §12).
- Дальше (v6): вынести схемы Horizon в **protobuf** (`max-horizon-server/proto/`)
  и перевести Horizon-лобби на gRPC; сессионные пакеты остаются плоскими LE
  (типизация — через Rust-структуры в `max_net` с юнит-тестами на байты).
- **Критерий**: `max_net` собирается по .proto + таблицам protocol.md без чтения C++.

### 1.4 Динамическая верификация (RE-стенд) — по потребности, не блокирует
- Открытые вопросы стенда (журнал): финальная трассировка CRT→main (адреса
  готовы: вход 0x26C714, main 0x20884E — цепочка cmds_main2.txt, нужен BPLIST
  перед RUN); расширение каталога.
- **Расширение каталога функций — метод автора (backlog)**: у автора в IDA
  5706 подпрограмм, из них 1644 — библиотечные с именами (Watcom clib3r/plib3r
  и др.); метод из `max-port-site/documentation.md`: Open Watcom (wdis/wlib),
  сравнение сигнатур библиотечных .obj с бинарём, regex-скрипты Python.
  Задача: применить тот же метод к `maxrun.flat` → доименовать библиотечные
  функции в functions-named.csv (наш r2-каталог: 6857 функций, 159 с именами).
- Запускаются, когда нужна проверка поведения оригинала или полнота каталога.
- **Критерий**: каждый запуск закрывает конкретный вопрос из backlog и завершается
  документом в `max-original-dasm/tools/dosbox/`.

## 7. Правила работы

1. Критические изменения — сначала `git add -A && git commit` (введено после потери
   данных; применять неукоснительно).
2. Делегирование: сложный анализ → `deepseek-v4-pro` (Effort Max); код/скрипты →
   `deepseek-flash`; выход каждого субагента проверяется в основном потоке.
3. «Сделано» = артефакт-файл + проверка критерия; без файла — не сделано.
4. Тестовые данные игры — копии из `build/server-run`, не из `max-original` напрямую.
5. Спецификации — единственный интерфейс между линиями: крейты пишутся по `docs/`
   и `formats/`, а не по C++-коду.

## Приложение A — Установленные факты RE (справочно)

- Формат: MZ + DOS/32A v9.1.2 (bound) + LE (заголовок 0x6B90); объекты 1-базовые:
  #1 код 0x10000 (0x12D469), #2 ISR COM2 0x140000, #3 данные 0x150000 (0x6F170).
- Статический вход игры: **0x10C704** (плоский образ `maxrun.flat`, base 0x10000).
- **Рантайм (решено)**: obj#1 база 0x170010, вход **0x26C714**, формула
  `runtime = static + 0x160010`, main() = 0x20884E, main_menu() = 0x211E10;
  CS приложения = 1038 (плоский). Стоп-якорь: 1048:2714 (цикл apply_fixups).
- Каталог: radare2 (с LE-fixups) — 6857 функций; 159 с именами файлов C++;
  розеттский камень: 18 372 строки, 2583 → файлы C++.
- Подробности: `max-original-dasm/README.md`, `TOOLS.md`,
  `tools/dosbox/entry-strategy.md`, `tools/dosbox/runtime-placement.md`.
