# PLAN.md — Генеральный план: RE оригинальной M.A.X. и Rust-клиент под Horizon

Версия: 4.0 · 2026-11-14
История: v1 — P2P-арбитр; v2 — клиент-сервер на C++; v3 — RE + Rust-клиент (постановка).
v4 — детальный исполнимый план с задачами, командами и критериями приёмки.

## 1. Цель

Переписать клиент M.A.X. (Interplay, 1996) на **Rust** с чистой модульной архитектурой,
изначально заточенной под **клиент-сервер**: игровым авторитетом остаётся headless-сервер
C++-порта, оркестрацию сессий ведёт **Horizon** (`max-horizon-server`, Rust). Оригинальная
игра разбирается (статически и динамически) как источник истины; C++-порт (`src/`) —
розеттский камень и оракул (те же имена функций/структур/констант).

### Принципы
1. **Сервер-авторитет**: клиент шлёт ввод/приказы, сервер возвращает снапшоты состояния.
2. **Модульность**: `core` не знает про сеть; `net` не знает про рендер; `assets` — чистые
   парсеры; `app` — тонкий клеевой слой.
3. **RE — ради спецификаций, а не полноты**: цель — точные структуры состояния, форматы
   файлов и контракт протокола, достаточные для переписывания; не «разобрать каждый байт».
4. **Всё в git**: каждый артефакт — файл в репозитории; критичные изменения — коммит
   (правило введено после потери данных 2026-11-13).
5. **Делегирование**: сложный анализ → субагенты `deepseek-v4-pro` (Effort Max);
   код/скрипты → субагенты `deepseek-flash`; результаты валидируются в основном потоке.

## 3. Инструментарий

- **Статика**: radare2 (ubuntu:24.04 в Docker); Ghidra 11.3.2 headless (образ `max-ghidra`,
  `tools/ghidra/analyze.sh`, entry 0x10C704, экспорт functions/strings/xrefs);
  `le_flat.py` (LE→flat), `match_strings.py` (строки → файлы C++).
- **Динамика**: DOSBox-X 2022.09 + отладчик (собран, `tools/dosbox-x/`); рантайм-образ
  `max-dosbox`; PTY-драйвер `re_drive.py` (команды/WAIT/F-клавиши); парсер трасс
  `parse_trace.py`; цепочки команд `cmds_*.txt`. Вход в отладчик — DOS-команда
  `DEBUGBOX`; после пейджера (GDT/HELP) — `Q`.
- **Модели делегирования**: Pro — анализ/рассуждения; Flash — код/скрипты.
- Подробности и адреса: `max-original-dasm/TOOLS.md`, `tools/dosbox/entry-strategy.md`,
  `tools/dosbox/runtime-mapping-analysis.md`.

## 4. Линия RE (`max-original-dasm/`)

### RE1 — Формат и инструменты ✅ выполнено
Формат (MZ + DOS/32A bound + LE), 3 объекта (код 0x10000 / ISR COM2 0x140000 /
данные 0x150000; нумерация объектов 1-базовая), плоский образ (`maxrun.flat`),
статический вход **0x10C704** (`EB 76` через баннер WATCOM), 18 372 строки,
2583 совпадения со строками C++.

### RE2 — Карта кода (адрес → имя → структуры)
**2.1 Рантайм-размещение — ОДИН ЗАМЕР ДО РЕЗУЛЬТАТА**
- Задача: на якоре INT21 (стоп CS=1048/EIP=2714) снять стек клиента
  (`DV 50:7C0`) → адрес возврата = адрес в коде игры → точное рантайм-размещение
  объекта #1 и формула `runtime = f(static)`.
- Кандидаты проверены/опровергнуты: 0x20D714 (стаб INT21), 0x26C714 (XMS-блок
  0x170000 + 0xFC704). XMS-блок DOS/32A = 0x170000, 62.5 МБ (команда `DOS XMS`).
- Критерий: файл `tools/dosbox/runtime-placement.md` с формулой и цепочкой BP до
  `main()`; стоп на `main` (статический 0x1A883E) подтверждён.

**2.2 Трассировка CRT → main**
- Задача: цепочка BP через `__astart` (0x10C77C), `__InitRtns` (0x127E72),
  `__cstart_` (0x127E22), lock-RT (0x13AA08) → `main` (0x1A883E) →
  `main_menu` (0x1B1E00) с адресами в рантайм-форме.
- Критерий: `tools/dosbox/main-trace.md` — последовательность стопов с регистрами
  (аргументы main: argc/argv).

**2.3 Каталог функций `functions.csv`**
- Задача: Ghidra-функции × xref строк × `string-matches.csv` → таблица
  `address, name (C++), file, purpose, calls, called_by`.
- Критерий: ≥ 200 функций с осмысленными именами C++ (ядро: GameManager_*,
  AiPlayer_*, UnitsManager_*, ResourceManager_*, меню), покрытие ≥ 60% строк-якорей.

**2.4 Структуры состояния**
- Задача: раскладки `UnitInfo`, `TeamInfo`, `GameManager` (и пр. из заголовков C++)
  сверены с доступом в коде (обращения по смещениям в Ghidra).
- Критерий: `structures.md` — каждая структура: поля, смещения, размер, сверка с
  C++-заголовком; плюс адреса глобального состояния GameManager.

### RE3 — Форматы данных (вход для `max_assets`)
По одному документу в `formats/` с полями, смещениями и байтовыми примерами;
первичный источник — загрузчики C++-порта (resource_manager.cpp и пр.), байты —
из файлов игры.
- **3.1 RES/PATCHES** — контейнер ресурсов (приоритет №1; от него зависит всё).
- **3.2 WRL/SCE/MPS** — карты, сценарии, параметры миссий.
- **3.3 SPW** — спрайты; **3.4 FLC** — анимации; **3.5 FON** — шрифты.
- **3.6 MSC/MVE** — музыка/ролики.
- Критерий: `formats/<format>.md` × 7; для RES — парсер на Python (проверен на
  PATCHES.RES) как эталон для Rust.

### RE4 — Протокол оригинала (историческая справка)
- Задача: пакеты, хендшейк, lockstep (из сетевого слоя C++-порта + при желании —
  динамика). Документируется как справка; новый клиент использует протокол Horizon.
- Критерий: `formats/original-net.md`.

## 5. Линия спецификаций (`docs/`)

- **`docs/protocol.md`** — контракт клиент↔Horizon: WS-лобби, тикеты, UDP-сессия,
  хендшейк, снапшоты состояния, команды (move/attack/build), конец хода, чат,
  реконнект (SNAP). Источник: сетевой слой C++-порта + коды сессий Horizon.
  Критерий: каждый тип сообщения с полями и направлением; по нему пишется `max_net`.
- **`docs/state-model.md`** — модель состояния сервера: что входит в снапшот,
  какие структуры зеркалятся в `max_core` (из RE2.4).
- **`docs/dedicated-server-plan.md`** — эксплуатация C++-headless под Horizon
  (уже существует; поддерживать в актуальном состоянии).

## 6. Линия Rust-клиента (`client-rust-port/`)

### R1 — Каркас ✅ выполнено
Workspace: `max_core` (чистая модель), `max_net` (WS+UDP), `max_assets`, `max_render`,
`max_app`; `cargo check/test` зелёные.

### R2 — Подключение к Horizon и рендер мира
- **2.1 `max_assets`**: парсер PATCHES.RES (по RE3.1) + таблицы ресурсов.
  Критерий: юнит-тесты читают реальные спрайты/карты из копий данных игры.
- **2.2 `max_net`**: WS-лобби → тикет → UDP-сессия → хендшейк → приём снапшота.
  Критерий: интеграционный тест с живым Horizon + headless (Docker).
- **2.3 `max_render`**: SDL3-окно, карта (по RE3.2), спрайты юнитов (по RE3.3).
  Критерий: рендер мира из снапшота сервера без расхождений с C++-клиентом.
- **2.4 `max_app`**: связка core↔net↔render↔assets; лог событий.
- Критерий фазы: Rust-клиент видит список игр Horizon, входит в сессию и рендерит
  мир и юнитов с серверного состояния.

### R3 — Играбельность
- Ввод: выделение юнитов, приказы (move/attack/build) → сервер; подтверждения;
  конец хода; чат; предпросмотр маршрута.
- Критерий: два Rust-клиента играют партию против headless 10+ ходов без расхождений
  состояния (сверка снапшотов).

### R4 — Доводка
- Реконнект (SNAP), спектатор, звук/ролики (MSC/FLC по RE3), CI-сборки, README.
- Критерий: переживает разрыв сети, спектатор подключается к живой партии.

## 8. Правила работы

1. Критические изменения рабочей области — сначала `git add -A && git commit`.
2. Делегирование строго по конвенции раздела 3; выход каждого субагента проверяется.
3. Каждая задача — артефакт-файл с критерием приёмки; «сделано» = файл + проверка.
4. Динамические сеансы DOSBox-X — по цепочкам `cmds_*.txt`; результаты — через
   `parse_trace.py` в `trace.csv`, затем документ.
5. Копии данных игры для тестов — из `build/server-run` (PATCHES.RES, help.json,
   language.json, maxint.json) — не из `max-original` напрямую.

## 9. Риски и контрмеры

| Риск | Контрмера |
|---|---|
| Рантайм-размещение кода меняется от конфигурации | замер стека в каждом сеансе; формула в runtime-placement.md |

| Ghidra на raw-бинарнике даёт неполные функции | якоря строк (define_strings) + ручные entry; сверка с C++ |

| Потеря файлов | git-коммиты после каждой критичной операции |
