# PLAN.md — Rust-клиент M.A.X. под Horizon (целевой план)

Версия: 5.0 · 2026-11-14
История: v1 — P2P-арбитр; v2 — клиент-сервер на C++; v3 — RE + Rust (постановка);
v4 — детальный план, ориентированный на RE. **v5 — переписан под новые цели:
главное — готовый Rust-клиент; RE и C++-порт — источники знаний, а не самоцель.**

## 0. Цели

1. **Цель 1 — Спецификации**: извлечь из C++-порта (основной источник) и оригинала
   (верификация) ровно то знание, которое нужно клиенту: модель состояния, форматы
   ресурсов, контракт протокола.
2. **Цель 2 — Rust-клиент**: модульный клиент (core/net/assets/render/app), который
   входит в Horizon-сессию и играет против headless-сервера.
3. **Цель 3 — Интеграция и эксплуатация**: Horizon-контракт, реконнект, спектатор,
   CI, документация.

### Принцип источников (новое в v5)
- **C++-порт (`src/`) — основной источник истины**: имена, структуры, константы,
  загрузчики форматов, сетевой слой уже написаны. Сначала читаем его.
- **RE оригинала (`max-original-dasm/`) — верификация и пробелы**: включается там,
  где C++-порт неясен или нужна проверка байтов/поведения оригинала.
- Ничего не реверсим «на будущее»: каждый RE-артефакт привязан к конкретной
  потребности крейта или спецификации.

## 1. Целевая картина

Готовый продукт: Rust-клиент M.A.X., который по `docs/protocol.md` входит в сессию
Horizon, рендерит мир и юнитов из авторитетных снапшотов headless-сервера, отправляет
приказы и играет партию 10+ ходов; переживает разрыв сети (SNAP), поддерживает
спектатора. Все игровые данные читаются из оригинальных ресурсов (`PATCHES.RES` и др.).

## 3. Цель 1 — Спецификации

Порядок работы: взять из C++-порта → оформить в `docs/` или `formats/` → сверить с
байтами оригинала (где нужно) → пометить «проверено RE».

### 1.1 Модель состояния → `docs/state-model.md` + `max-original-dasm/structures.md`
- Источник: заголовки C++ (`src/*.h`: UnitInfo, TeamInfo, GameManager, миссии,
  ресурсы, приказы) + сериализация headless.
- Задача: описать снапшот: какие структуры, какие поля, как кодируются.
- RE-верификация (по потребности): сверка смещений с обращениями в коде оригинала
  (Ghidra, якоря строк) — только для структур, где важна двоичная совместимость.
- **Критерий**: по state-model.md можно написать `max_core` без чтения C++.

### 1.2 Форматы ресурсов → `max-original-dasm/formats/<format>.md`
- Источник: загрузчики C++ (`resource_manager.cpp` и пр.) + байты из `max-original/`.
- Приоритет: **RES/PATCHES** (контейнер, всё остальное через него) → карты
  (WRL/SCE/MPS) → спрайты (SPW) → анимации (FLC) → шрифты (FON) → звук/ролики (MSC/MVE).
- **Критерий**: по каждому документу Flash-агент пишет парсер в `max_assets` без
  обращения к C++-коду; RES дополнительно имеет эталонный Python-парсер.

### 1.3 Протокол клиент↔Horizon → `docs/protocol.md`
- Источник: сетевой слой C++ + коды сессий `max-horizon-server` + PLAN v2 (раздел 4).
- **Критерий**: каждый тип сообщения (WS-лобби, тикет, UDP-хендшейк, снапшот,
  дельта, приказы, конец хода, чат, SNAP) с полями и направлением.

### 1.4 Динамическая верификация (RE-стенд) — по потребности, не блокирует
- Открытые вопросы стенда (журнал): рантайм-размещение кода (замер стека на якоре
  INT21, `DV 50:7C0`), трассировка CRT→main, каталог `functions.csv` (имена C++).
- Запускаются, когда нужна проверка поведения оригинала (ИИ, правила, редкие
  форматы) или полнота каталога для разбора конкретной функции.
- **Критерий**: каждый запуск закрывает конкретный вопрос из backlog и завершается
  документом в `max-original-dasm/tools/dosbox/`.

## 4. Цель 2 — Rust-клиент

### R1 — Каркас ✅ выполнено
Workspace `client-rust-port` (core/net/assets/render/app), `cargo check/test` зелёные.

### R2 — Сессия Horizon + рендер мира
- **2.1 `max_assets`** — парсер PATCHES.RES по 1.2 + таблицы ресурсов.
  Критерий: тесты читают спрайты/карты из копий данных (`build/server-run`).
- **2.2 `max_net`** — WS-лобби, тикет, UDP-сессия, хендшейк, приём снапшота по 1.3.
  Критерий: интеграционный тест с живым Horizon + headless в Docker.
- **2.3 `max_render`** — SDL3-окно, карта и спрайты по 1.2.
  Критерий: рендер мира из снапшота.
- **2.4 `max_app`** — связка; события; лог.
- **Критерий фазы**: клиент видит список игр Horizon, входит в сессию, рендерит
  мир и юнитов с серверного состояния.

### R3 — Играбельность
- Приказы юнитам (move/attack/build) → сервер; подтверждения; конец хода; чат;
  предпросмотр маршрута.
- **Критерий**: два Rust-клиента играют партию против headless 10+ ходов без
  расхождений снапшотов.

### R4 — Эксплуатация
- Реконнект (SNAP), спектатор, звук/ролики, CI-сборки, README.
- **Критерий**: разрыв сети переживается; спектатор входит в живую партию.

## 5. Цель 3 — Интеграция с Horizon

- Зафиксировать контракт 1.3 на уровне кода `max_net` и тестов: фикстуры сообщений,
  интеграционный smoke (Horizon + headless в Docker, как в `build/horizon-smoke.py`).
- **Критерий**: `max_net` проходит smoke против реального Horizon без изменений сервера.

## 7. Правила работы

1. Критические изменения — сначала `git add -A && git commit` (введено после потери
   данных; применять неукоснительно).
2. Делегирование: сложный анализ → `deepseek-v4-pro` (Effort Max); код/скрипты →
   `deepseek-flash`; выход каждого субагента проверяется в основном потоке.
3. «Сделано» = артефакт-файл + проверка критерия; без файла — не сделано.
4. Тестовые данные игры — копии из `build/server-run`, не из `max-original` напрямую.
5. Спецификации — единственный интерфейс между линиями: крейты пишутся по `docs/`
   и `formats/`, а не по C++-коду.

## 8. Риски и контрмеры

| Риск | Контрмера |
|---|---|
| C++-порт расходится с оригиналом в деталях | точечная RE-верификация спорных мест (1.4) |
| Неполные знания о протоколе Horizon | фикстуры и smoke-тест (Цель 3) |
| Расхождение клиента с сервером | сервер-авторитет + SNAP; сверка снапшотов в тестах R3 |
| Потеря файлов | git-коммиты после каждой критичной операции |
| Медленный DOSBox-X (динамика) | паузы WAIT 90–180; запускать только по backlog 1.4 |

## Приложение A — Установленные факты RE (справочно)

- Формат: MZ + DOS/32A v9.1.2 (bound) + LE (заголовок 0x6B90); объекты 1-базовые:
  #1 код 0x10000 (0x12D469), #2 ISR COM2 0x140000, #3 данные 0x150000 (0x6F170).
- Статический вход игры: **0x10C704** (плоский образ `maxrun.flat`, base 0x10000).
- Динамика: T=0x54C; XMS-блок DOS/32A = 0x170000 (62.5 МБ); якорь — клиент INT21
  (CS=1048, EIP=2714, Pr16); рантайм-размещение объекта #1 — открытый вопрос
  (гипотезы 0x20D714/0x26C714 опровергнуты). Адреса CRT: `__astart` 0x10C77C,
  `__InitRtns` 0x127E72, `__cstart_` 0x127E22, main 0x1A883E, main_menu 0x1B1E00.
- Розеттский камень: 18 372 строки, 2583 → файлы C++.
- Подробности: `max-original-dasm/README.md`, `TOOLS.md`,
  `tools/dosbox/entry-strategy.md`, `tools/dosbox/runtime-mapping-analysis.md`.
