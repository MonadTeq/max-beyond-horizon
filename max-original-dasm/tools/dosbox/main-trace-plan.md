# M.A.X. (MAXRUN.EXE) — план трассировки от входа игры до main()

Дата: 2026-11-14. Дополняет `entry-strategy.md` и `runtime-mapping-analysis.md`.

## 0. TL;DR

| Точка | Статика (flat, base 0x10000) | Рантайм-линейный | Через селекторы |
|---|---|---|---|
| LE-вход (`EB 76` через баннер) | **0x10C704** | **0x20C714** | `BP 1038:20C714` / `BP 1048:1714` |
| `__astart` (старт CRT после баннера) | **0x10C77C** | **0x20C78C** | `BP 1038:20C78C` / `BP 1048:178C` |
| `__InitRtns` (диспетчер init-таблицы) | **0x127E72** | **0x227E82** | `BP 1038:227E82` / `BP 1048:1CE82` |
| `__cstart_` (C-стартап, зовёт main) | **0x127E22** | **0x227E32** | `BP 1038:227E32` / `BP 1048:1CE32` |
| `__lock` RT-сегмента (вызов из `__cstart_`) | **0x13AA08** | **0x23AA18** | `BP 1038:23AA18` / `BP 1048:2FA18` |
| **`main()`** | **0xA883E** | **0x1A884E** | `BP 1038:1A884E` (через 1048 нельзя — ниже базы) |
| `main_menu()` (сразу после main) | **0xB1E00** | **0x1B1E10** | `BP 1038:1B1E10` |
| `__FiniRtns` (fini-диспетчер, путь выхода) | **0x127EBD** | **0x227ECD** | `BP 1038:227ECD` / `BP 1048:1CECD` |

Основная гипотеза рантайм-маппинга: **runtime = static + 0x100010**
(база объекта #1 = 0x110010 = XMS-блок 0x110000 + 0x10). Альтернативы и проверка —
раздел 5.

## 1. Как устроен стартовый код (разобрано по flat-образу)

Вход (проверено байтами `EB 76` в `maxrun.flat` @ 0xFC704 и в EXE @ 0x137204):

```
0x10C704: EB 76            jmp 0x10C77C        ; перепрыгивает баннер
0x10C706: "WATCOM C/C++32 Run-Time system. (c) ... 1988-1995. All rights reserved."
0x10C770: '.' 8D 40 00     03 00 00 00 "con",0  ; выравнивание + данные CRT
0x10C77C: FB               sti                 ; === __astart ===
0x10C77D: 83 E4 FC         and esp,-4
0x10C780: 89 E3            mov ebx,esp
0x10C782: 89 1D 74 E5 01 00 mov [0x1E574],ebx  ; __STKTOP
0x10C78E: 66 B8 24 00      mov ax,0x24         ; PSP-сегмент
0x10C792: 66 A3 6C E5 01 00 mov [0x1E56C],ax
0x10C798: BB 52 41 48 50   mov ebx,'HPAR'      ; магия детекта DOS/4GW
0x10C79D: 29 C0 / B4 30 / CD 21                ; int 21h AX=3000 (версия DOS)
0x10C7B7: C1 E8 10 / 66 3D 58 44   cmp ax,'XD' ; DOS/4GW? (совместимо: DOS/32A)
0x10C7FE: 66 3D 43 42               cmp ax,'CB' ; Causeway?
0x10C838: 66 BA 78 00 / 66 B8 00 FF / CD 21     ; иначе DPMI-проба
... (путь сливается в 0x10C891: сохранение PSP/env)
0x10C8B4: mov es,[0x1E56C]      ; ES = PSP
0x10C8BB: mov edx,0x6C170       ; буфер командной строки (DGROUP)
0x10C8C9: mov cl,es:[edi-1]     ; длина cmdline из PSP:0x80
0x10C8CD: B0 20 / F3 AE         ; пропуск ведущих пробелов
0x10C8E3: F3 A4                 ; копия cmdline в DGROUP
0x10C8F8: cmp eax,0x37386F6E    ; поиск "no87=" в окружении
0x10C938: mov ecx,0x6C170 / mov edi,0x23180
0x10C963: F3 AB / F3 AA         ; ОБНУЛЕНИЕ BSS [0x23180..0x6C170]
0x10C982: B8 FF 00 00 00 / call 0x127E72   ; __InitRtns (см. ниже)
0x10C98C: 29 ED / call 0x127E22              ; __cstart_ (см. ниже)
0x10C993: jmp 0x10C9B8                       ; путь выхода
0x10C9B8: B8 00 00 00 00 / BA FF 00 00 00 / call 0x127EBD  ; __FiniRtns
0x10C9C7: B4 4C / CD 21                      ; terminate
```

Функции CRT (все адреса статические):

- **0x127E72 = `__InitRtns`** (диспетчер инициализации Watcom): обходит
  таблицу 6-байтных записей `{status, priority, addr}` от 0x22F92 до 0x23052,
  вызывает записи в порядке приоритета (`cmp [esi+1],al / ja`), помечает
  status=2. Симметричный **0x127EBD = `__FiniRtns`** обходит таблицу
  0x23052..0x23064 (3 записи). Адреса в таблицах — цели LE-fixup'ов,
  поэтому в flat-файле они «сырые»; сами диспетчеры — rel32-код, адреса
  достоверны.
- **0x127E22 = `__cstart_`** (C-стартап):
  ```
  push edx; push ebp; mov ebp,esp
  mov edx,[0x1E578]          ; __STACKLOW
  add edx,3; and dl,0xFC
  call 0x13470F              ; __STK (проверка стека)
  ...
  mov [0x1E57C],eax          ; __STKTOP
  call 0x13AA08              ; lock RT-кода 0xFC9D0..0xFC9DB (DPMI 0x600)
  mov edx,[0x6BD44]          ; argv
  mov eax,[0x6BD40]          ; argc
  call 0xA883E               ; ======= MAIN =======
  call 0x10C65F              ; term/abort-диспетчер (если main вернулся)
  ```
- **0xA883E = `main()`** — идентификация железобетонная: тело в точности
  повторяет `src/main.cpp` порта и использует константы из
  `src/resourcetable.hpp`:
  ```
  push 0x20; call 0x105D52        ; __CHK-пролог Watcom
  mov [ebp-4],eax; mov [ebp-8],edx
  call 0xA83BB(eax=argc,edx=argv) ; разбор командной строки (цикл по argv,
                                  ; сравнения с опциями через 0x119010)
  call 0xA6A9C                    ; инициализация ресурсов/игры
  call 0xB57FF                    ; интро (если 0 -> логотип ILOGO)
  call 0xA8794(eax=0x6E7,edx=0xBB8)  ; menu_draw_logo(ILOGO=0x6E7, 3000=0xBB8)
  call 0xDCf8E(eax=0x27278,edx=0x6A5,ebx=0) ; PlayMusic(MAIN_MSC=0x6A5, false)
  call 0xA8794(eax=0x6E8,edx=0xBB8)  ; menu_draw_logo(MLOGO=0x6E8, 3000)
  call 0xB1E00                    ; main_menu()
  ret
  ```
  `ILOGO=0x6E7`, `MLOGO=0x6E8`, `MAIN_MSC=0x6A5` — точные совпадения с
  `resourcetable.hpp:1730,1796,1797`.

Полный дизасм ключевых участков сохранён в артефактах:
`tools/dis_astart.txt` (0x10C600..0x10CB20), `tools/dis_cstart.txt`
(0x127E00..0x128200), `tools/dis_a883e.txt` (0xA8700..0xA8A50),
`tools/dis_13aa08.txt`. Инструмент: `tools/dis_region.py` (capstone).

## 2. Рантайм-маппинг: почему вход = 0x20C714, а не 0x20D714

Разбор лога предыдущего сеанса (`dosbox-out.txt`) показал, что стоп
«на входе» на самом деле был в **клиентском 16-битном API DOS/32A**
(«soul»), а не в 32-битном коде игры:

- На стопе `BP 20D71:4` регистры: **CS=1048, EIP=0x2714, Pr16** (16-битный
  PM-код!), SS=0050/DS=0058/ES=0068/FS=0050 (селекторы ядра), GS=1040
  (плоские данные приложения), ESP=0x7C0 (стек ядра).
- Код-вью на стопе: `1048:2714: EB DF jmp 0x26F5; mov gs:[di],al; ret;
  mov gs:[di],ax; ret; add eax,edx; ...` — таблица 16-битных API-стабов
  клиента. Эти же байты есть в стабе EXE по смещению 0x5564 (не в LE-образе).
- GDT на стопе: `1030`=объект#2 (ISR, база 0x29D490, лимит 0x16B),
  `1038`=**32-битный код, база 0, 4GB** (плоский селектор приложения),
  `1040`=**32-битные данные, база 0, 4GB**, `1048`=16-битный код,
  **база 0x20B000** (окно клиента), лимит 0xFFFF.
- `0x20B000 + 0x2714 = 0x20D714` — то есть `BP 20D71:4` попал в стаб
  клиента `INT 21h` (первый же `int 21h` из `__astart`, AX=3000). По линейному
  адресу матч в PM идёт через `GetAddress(CS,EIP)` (см. `debug.cpp:401`), поэтому
  стоп сработал — но это был клиент, а не вход игры.

Правильная база объекта #1 по исходникам DOS/32A (`loader.asm:alloc_block/
alloc_dpmi_mem` + конфиг): XMS-блок 0x110000, выравнивание на параграф
(`_misc_byte2`=0x09 в ID32-конфиге EXE @ 0x95 — бит page-align не взведён)
→ **база = 0x110010**, сдвиг относительно статики (base 0x10000):

```
runtime = static + 0x100010
вход    = 0x110010 + 0xFC704 = 0x20C714
```

В `create_selector` (loader.asm:578) для 32-битного объекта #1 (flags=0x2045,
бит 0x2000 установлен) селектор кода — **плоский, база 0, лимит 4GB**
(`_sel32_cs`, в GDT это 1038), а `_app_eip += база` (строка 614) даёт
EIP=0x20C714. Поэтому **весь 32-битный код игры исполняется с CS=1038
и линейный адрес = EIP**; `main` (0x1A884E) лежит НИЖЕ базы селектора 1048
(0x20B000), и форма `BP 1048:…` для него в принципе невозможна (отрицательный
оффсет) — только `BP 1038:1A884E`.

`0x20D714` при этом остаётся полезной точкой: это стаб клиента `INT 21h`
(останов на первом DOS-вызове игры).

## 3. Формы адресов для BP (по debug.cpp этого форка)

`GetAddress(seg,off)` (debug.cpp:401):
- в реальном режиме: `seg<<4 + off` (линейный), если seg != CS;
- в защищённом режиме: `LinMakeProt(seg,off)` — seg трактуется как СЕЛЕКТОР.

Следствия:
1. В **PM** (наш стоп) «RM-форма» `BP 20C71:4` НЕ работает (0x20C71 не
   селектор) — нужна форма `BP 1038:…` (плоский код, оффсет = линейный адрес)
   или `BP 1048:…` (для адресов >= 0x20B000: оффсет = L−0x20B000).
2. В **RM** (свежий сеанс до запуска игры) работают линейные формы
   `BP seg:off` (seg=L>>4, off=L&0xF), но INT3, записанный в RM до загрузки
   игры, будет затёрт загрузчиком DOS/32A. Поэтому линейные RM-формы годятся
   только если создавать их на промежуточном стопе ПОСЛЕ загрузки объекта
   (как в cmds_c.txt), либо не зависеть от них вовсе (наш путь).
3. Нумерация BP в этом форке — **с 0**, список хранится новыми вперёд
   (`push_front`), т.е. последний созданный BP = номер 0.
4. `BP` в PM пишет 0xCC в линейный адрес, вычисленный при создании; матч —
   по линейному адресу исполнения, селектор не важен.

## 4. Таблица адресов (все формы)

Основная дельта **0x100010**. Альтернативы: 0x100000 (если page-align) и
0x101010 (прежняя гипотеза, см. раздел 5).

| Точка | статика | +0x100010 | RM-форма (создание в RM после загрузки) | PM: 1038 | PM: 1048 |
|---|---|---|---|---|---|
| LE-вход | 0x10C704 | 0x20C714 | 20C71:4 | 1038:20C714 | 1048:1714 |
| __astart | 0x10C77C | 0x20C78C | 20C78:C | 1038:20C78C | 1048:178C |
| __InitRtns | 0x127E72 | 0x227E82 | 227E8:2 | 1038:227E82 | 1048:1CE82 |
| __cstart_ | 0x127E22 | 0x227E32 | 227E3:2 | 1038:227E32 | 1048:1CE32 |
| lock RT | 0x13AA08 | 0x23AA18 | 23AA1:8 | 1038:23AA18 | 1048:2FA18 |
| **main** | **0xA883E** | **0x1A884E** | 1A884:E | 1038:1A884E | — (ниже базы) |
| main_menu | 0xB1E00 | 0x1B1E10 | 1B1E1:0 | 1038:1B1E10 | — |
| __FiniRtns | 0x127EBD | 0x227ECD | 227EC:D | 1038:227ECD | 1048:1CECD |
| стаб клиента INT21 | — | 0x20D714 | 20D71:4 | — | 1048:2714 |

То же при дельте **0x100000** (все линейные −0x10):
вход 0x20C704, __astart 0x20C77C, __InitRtns 0x227E72, __cstart_ 0x227E22,
main 0x1A883E, main_menu 0x1B1E00.

То же при дельте **0x101010** (все линейные +0x1000 от основной):
вход 0x20D714, __astart 0x20D78C, __InitRtns 0x228E82, __cstart_ 0x228E32,
main 0x1A984E, main_menu 0x1B2E10.

## 5. Почему 0x100010, и как проверить в сеансе

- XMS-блок #1 = 0x110000 (memsize=64 в конфиге сеанса); `alloc_dpmi_mem`
  выравнивает на параграф, пул DOS/32A даёт +0x10 → база 0x110010.
- Проверка в сеансе: на стопе у входа выполнить `DV 20C714` (дамп памяти) —
  там должны быть байты `EB 76 57 41 54 43 4F 4D` (jmp + баннер «WATCOM…»).
  Если баннер окажется на 0x20C704 — дельта 0x100000; если на 0x20D714 —
  дельта 0x101010 (тогда заменить адреса по таблице выше).
- Дополнительная проверка в логе: на стопе `__InitRtns` код-вью должен
  показывать `push ebx; push edx; push es; mov edx,eax; mov esi,0x22F92…`,
  на стопе main — `push 0x20; call …; push ebx…` (см. dis-артефакты).

## 6. Цепочка cmds_main.txt (что происходит)

Файл самодостаточен для свежего сеанса (прелюдия повторяет cmds_c.txt):

1. Семь BP прелюдии (в RM) доводят сеанс до стопа на **0x20D714** (стаб
   клиента INT21, CS=1048 EIP=2714) — 5 промежуточных стопов обслуживаются
   парами RUN/WAIT/GDT/Q.
2. На стопе: `BPDEL 1` (убрать BP 20D71:4 — иначе стоп на КАЖДОМ int 21h),
   `BPDEL 0` (20D72:4). Нумерация с 0, новые вперёд.
3. Новые BP через плоский селектор `1038` (создаются уже в PM, объект
   загружен, INT3 пишется прямо в код игры): __InitRtns 0x227E82,
   __cstart_ 0x227E32, lock-RT 0x23AA18, **main 0x1A884E**, main_menu 0x1B1E10.
4. Пять циклов RUN/WAIT/GDT/Q — по одному на каждый стоп. На каждом стопе
   в логе: регистры (CS=1038, EIP=линейный адрес), код-вью (сверка с
   dis-артефактами), GDT (идентификация селекторов).
5. Финальный `BPLIST` + RUN/WAIT 30 — игра уходит в меню (в логе:
   VGA-инициализация, 640x480 и т.п.).

Порядок стопов ожидаемый: __InitRtns (0x227E82) → __cstart_ (0x227E32) →
lock-RT (0x23AA18) → **main (0x1A884E)** → main_menu (0x1B1E10).
