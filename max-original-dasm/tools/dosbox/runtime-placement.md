# MAXRUN.EXE — точное рантайм-размещение (объект #1) из стека стопа 1048:2714

Сессия: memsize=64, DOS/32A v9.1.2 bound, XMS-блок DOS/32A = 0x170000 (62.5 МБ).
Стоп: `BP 20D71:4` → CS=1048, EIP=0x2714, линейный 0x20D714.

## 0. Вердикт: что это за стоп

Это **не** клиент INT 21h и **не** код игры. BP-ловушка (INT3, 0xCC в 0x20D714)
попала в **цикл применения fixups загрузчика DOS/32A** (`apply_fixups`,
loader.asm), инструкция `jmp @@5` (клиент-оффсет 0x2714 = файл 0x5564 = `EB DF`).
Доказательства:

- В файле MAXRUN.EXE клиент начинается с 0x2E50 (MZ-entry `start` = 0x5ABC =
  0x2E50+0x2C6C, дизасм байтов совпадает с исходником dos32a.asm).
  0x2714+0x2E50 = 0x5564 → `EB DF` = `jmp 0x5545` (= `@@5: pop edi; pop ecx;
  cmp esi,ecx; jb @@0` в apply_fixups). В стеке — INT3-фрейм EIP=0x2714,
  CS=0x1048, EFLAGS=0x246 (PF+ZF+IF+бит1; ZF=1 от `and si,0xf`/`add si,si`).
- Настоящий клиент INT21 (`_int21`) = клиент-оффсет **0x14BA** (файл 0x430A,
  сигнатура `FC 2E F7 06 4E 30 00 01` = cld + test cs:[_sys_misc],0100h) —
  не 0x2714.
- EAX=2 на стопе — значение fixup-записи (`fix_byte` пишет 0x02 в gs:[0x1CDC3F]),
  а не «функция INT21 02h». EDX в условии (0x291028) ошибочно снят из дампа
  SS:0x7A6; реальный EDX на стопе = база объекта #2 = 0x29D490.

Игра на этом стопе ещё **не запущена**: загрузчик применяет релокейшены к
объекту #1 (страница 0x5D из 0x12E). Поэтому возвратного адреса «в игру» в
стеке нет — но стек содержит таблицу загрузки объектов, которая даёт точное
рантайм-размещение (см. §2–3).

## 1. Раскладка стека клиента INT21 (для справки; на этом стопе не активна)

Вход `_int21` (клиент Pr16, 1048:14BA), CPU-фрейм после `int 21h` из 32-битного
кода (10 байт, 32-битные пушы):

```
[esp+0]  = EIP (32)      — возврат в приложение (CS=1038, плоский)
[esp+4]  = CS  (16)
[esp+6]  = EFLAGS (32)
```
после `push ds es` + `pushad` (32-битный, 66 60):
```
[esp+0]=EDI [esp+4]=ESI [esp+8]=EBP [esp+C]=ESP_orig
[esp+10]=EBX [esp+14]=EDX [esp+18]=ECX [esp+1C]=EAX
[esp+20]=DS [esp+22]=ES [esp+24]=EIP [esp+28]=CS [esp+2A]=EFLAGS
```
Выход: `@__ok/@__err: popad; pop es ds; and [esp+8],0FEh / or …,1; iretd`.
Функция без спец-обработки (в т.ч. AH=02) уходит в `@__go21: popad; pop es ds;
jmp far 32 _int21_ip` (ядро → RM-редиректор int_matrix+4*21h).

## 2. Декодирование стека стопа (SS:0050, база 0xED40; ESP=0x7C0 до INT3)

| Смещ. | dword | Декодирование |
|---|---|---|
| 0x7A0..0x7B3 | 0x0020, 0x1028, 0x0029, 0x0008, 0x0002 | старые фреймы (структуры DPMI/RM-вызовов int31/int21 загрузчика) |
| 0x7B4 | 0x00002714 | **INT3-фрейм: EIP** (адрес BP-ловушки) |
| 0x7B8 | 0x00001048 | INT3-фрейм: CS |
| 0x7BC | 0x00000246 | INT3-фрейм: EFLAGS |
| 0x7C0 | **0x001CD010** | EDI, push apply_fixups = база obj#1 0x170010 + 0x5D·0x1000 (страница фиксапов) |
| 0x7C4 | 0x0001A457 | ECX, push apply_fixups = конец блока fixups страницы (ESI 0x1A327 + 0x130) |
| 0x7C8 | 0x2615 (word) | возврат в relocate_le_object (`@@2: pop eax`) |
| 0x7CA | 0x0000005D | счётчик страниц (93) |
| 0x7CE | 0x23E2 (word) | возврат в load_application (`@@4`) |
| 0x7D0 | 0x24; 0x130; **0x29D610**; 0x1028|0x2043 | **запись объекта #3** (npages=36, index=0x130, база, селектор/флаги) |
| 0x7E0 | 1; 0x12F; **0x29D490**; 0x1030|0x0045 | **запись объекта #2** (ISR COM2; сходится с GDT sel 1030: база 0x29D490, лимит 0x16B) |
| 0x7F0 | 0x12E; 1; **0x170010**; 0x1038|0x2045 | **запись объекта #1** (npages=302, index=1, база, код-селектор 0x1038) |

Формат записи — `load_application` делает `push edx; push edi; push esi; push ebx`
на объект: [+0]=#страниц, [+4]=индекс страницы, [+8]=**база загрузки**,
[+12]=селектор<<16|флаги. Поля совпадают с LE-таблицей объектов файла
(0x6C54: vsize 0x12D469/base 0x10000/flags 0x2045; 0x6C6C: 0x16B/0x140000/0x45;
0x6C84: 0x6F170/0x150000/0x2043) — записи в стеке достоверны.

Текущий fixup (по регистрам): ESI=0x1A327, запись {SRC/FLAGS=0x0000,
SRCOFF=0x0C2F, value=0x02} → `fix_byte`: запись 0x02 в gs:[EDI=0x1CDC3F]
(объект #1, оффсет 0x5BC2F). 0x1CD010 из «0x1Cxxxx» в условии — это база
страницы фиксапов в коде объекта #1, а не адрес в данных; пара слов
(0x2045,0x1038) на 0x7FC — поле селектора записи объекта #1, а не возвратный
CS:EIP (игра на стопе не исполнялась).

## 3. Рантайм-размещение (вывод из баз и GDT)

Пул XMS P = 0x170000. Раскладка: блок = заголовок 0x10 + данные
(параграфное выравнивание):

```
obj#1: данные @ P+0x10            = 0x170010   (vsize 0x12D469 → 0x12D470)
       след. блок @ 0x170000+0x10+0x12D470 = 0x29D480
obj#2: данные @ 0x29D480+0x10     = 0x29D490   (vsize 0x16B → 0x170)  ← GDT 1030 ✓
obj#3: данные @ 0x29D600+0x10     = 0x29D610   (vsize 0x6F170)
       конец = 0x306D780 = вершина стека приложения (ESP = база#3+LE.esp)
```
Проверка: 0x29D490 = 0x170010 + 0x12D480 ✓ (align16(vsize)+0x10 заголовка) —
точно совпадает с GDT sel 1030 (база 0x29D490, лимит 0x16B) и записью #2 стека.

Клиент/ядро (1048, база 0x20B000) — отдельный блок XMS, не между объектами.

**Точка входа игры:**

```
entry_runtime = база_объекта#1 + LE.eip = 0x170010 + 0xFC704 = 0x26C714
формула:      runtime = static + (база#1 − 0x10000) = static + 0x160010
              0x10C704 → 0x26C714
```

CS:EIP приложения на входе: **1038:26C714** (CS=1038 — плоский 32-бит код,
база 0, лимит 4 ГБ; линейный адрес = EIP). DS/SS приложения = 1028 (плоские
данные), ESP = 0x306D780.

Подтверждение байтами: статически 0x10C704 = файл 0x137204 =
`EB 76 57 41 54 43 4F 4D …` (`jmp +0x76` через баннер «WATCOM C/C++32
Run-Time system…») — проверено в EXE. Рантайм-проверка в PM:
**`DV 1038:26C714`** (или `BP 1038:26C714`) — должны быть те же `EB 76 "WATCOM"`.

Примечание к «0x20D714/0x26C714 опровергнуты»: 0x20D714 — это клиент DOS/32A
(данный стоп), входом не является; 0x26C714 по этим данным и есть вход —
проверять его нужно через **плоский селектор 1038** (`DV 1038:26C714`), а не
как сегмент (`DV 26C71:4` невалиден в PM: 0x26C71 не селектор).

## 4. Цепочка BP для поимки main (рантайм)

Дельта runtime = static + 0x160010. main статический = 0xA883E →
**main_runtime = 0x20884E**.

| Точка | статика | рантайм | BP (PM, плоский CS) | RM-форма (после загрузки объектов) |
|---|---|---|---|---|
| LE-вход (`EB 76`) | 0x10C704 | **0x26C714** | `BP 1038:26C714` | 26C71:4 |
| `__astart` | 0x10C77C | 0x26C78C | `BP 1038:26C78C` | 26C78:C |
| `__InitRtns` | 0x127E72 | 0x287E82 | `BP 1038:287E82` | 287E8:2 |
| `__cstart_` | 0x127E22 | 0x287E32 | `BP 1038:287E32` | 287E3:2 |
| `__lock` RT-сегмента | 0x13AA08 | 0x29BA18 | `BP 1038:29BA18` | 29BA1:8 |
| **`main()`** | **0xA883E** | **0x20884E** | `BP 1038:20884E` | 20884:E |
| `main_menu()` | 0xB1E00 | 0x211E10 | `BP 1038:211E10` | 211E1:0 |
| `__FiniRtns` | 0x127EBD | 0x287ECD | `BP 1038:287ECD` | 287EC:D |

Готовый скрипт (создание на стопе 1048:2714, объекты уже загружены):

```
BPDEL 1
BPDEL 0
BP 1038:26C714
BP 1038:26C78C
BP 1038:287E82
BP 1038:287E32
BP 1038:29BA18
BP 1038:20884E
BP 1038:211E10
RUN
WAIT 20
```
и далее на каждом стопе: `GDT` / `Q` / `RUN` / `WAIT 15`. Ожидаемый порядок
стопов: 26C714 → 287E82 → 287E32 → 29BA18 → **20884E (main)** → 211E10.

## 5. Итог

- Стоп 1048:2714 = загрузчик (apply_fixups), не INT21, не игра; возврата в игру
  в стеке нет (возвраты 0x2615 → relocate_le_object, 0x23E2 → load_application).
- Базы: obj#1 = 0x170010, obj#2 = 0x29D490, obj#3 = 0x29D610 (пул 0x170000).
- **runtime-entry = 0x26C714**, формула `runtime = static + 0x160010`,
  CS:EIP приложения на входе = **1038:26C714**.
- main() = **0x20884E** (статический 0xA883E); проверка входа — `DV 1038:26C714`
  → `EB 76 "WATCOM…"`.
