## 1. Общая структура файла

Файл — **линейная последовательность секций** без сжатия и без выравнивания, порядок байтов —
**little-endian** (формат DOS/x86). Структуры упакованы (в порте `Point` проверен
`static_assert(std::is_trivially_copyable)`; в файле паддинга нет). Сжатия на уровне WRL нет
(в порте ни одного вызова распаковки; тайлы — «сырые» пиксели).

```
+0x0000  u8[3]                сигнатура (3 байта, без NUL): "WRL"
+0x0003  u16 LE               layer_count — число слоёв
+0x0005  Point[layer_count]   размеры слоёв: по {int16 x; int16 y} (4 байта) на слой
+0x0009  u8[W*H]              миникарта — 1 байт на клетку = индекс палитры
+0x3109  u16[W*H]             карта tile-id (LE, row-major)
+0x9309  u16 LE               tile_count — число тайлов в наборе
+0x930B  u8[tile_count*64*64] пиксели тайлов: 64×64, 8 бит на пиксель, индексы палитры
+…       u8[768]              палитра: 256 цветов × 3 канала RGB (8 бит на канал)
+…       u8[tile_count]       pass-таблица: 1 байт на тайл, значения 0..3
```

Числовые смещения выше — для штатного случая `layer_count=1`, `W=H=112` (0x70),
поэтому `W*H = 12 544 = 0x3100`; они совпадают во **всех 24** реальных файлах.
`Point` = два `int16_t` (4 байта), см. `max-cpp-port/src/point.hpp`.

Формула размера файла (проверена на всех 24 файлах, сходится байт-в-байт):

```
size = 3 + 2 + 4*layer_count + W*H + 2*W*H + 2 + 4096*tile_count + 768 + tile_count
     = 38 411 + 4097*tile_count          (при layer_count=1, W=H=112)
tile_count = (size − 38 411) / 4097      (обратная проверка)
```

### 1.1. Заголовок (5 + 4·layer_count байт)

```c
// +0x0000
char    sig[3];        // "WRL" (57 52 4C) — 3 байта, без NUL
// +0x0003
uint16_t layer_count;  // LE: число слоёв (во всех реальных файлах = 1)
// +0x0005
struct { int16_t x; int16_t y; } dims[layer_count];  // по 4 байта, LE
```

- **Сигнатура информативна, но не проверяется**: загрузчик порта делает безусловный
  `fseek(fp, 3, SEEK_SET)` и ни с чем первые 3 байта не сравнивает. В `SNOW_1.WRL`
  сигнатура битая — `"DMO"` (`44 4D 4F`); файл при этом полностью валиден и грузится
  (в каталоге игры есть и сейвы `.DMO`, но их формат другой — SmartFile, см. §7.12).
- `layer_count` в реальных файлах всегда `01 00`. Портом читаются **все**
  `layer_count` записей размеров, но используется только `dims[0]` (как размер карты).
  В C++ буфер рассчитан на 12 записей (`Point map_layer_dimensions[12]`) — при
  `layer_count > 12` оригинал переполнил бы стек; Rust-парсеру — читать в `Vec`.
- `dims[0]` = (112, 112) во всех 24 файлах (`70 00 70 00`).

### 1.2. Миникарта (W·H байт)

Один слой `W*H` байт, row-major (`index = y*W + x`). Каждый байт — **индекс 256-цветной
палитры** из конца этого же файла (та же палитра, что и у тайлов): пиксель миникарты —
это 1 байт на клетку.

Порт читает **ровно один** слой (`map_minimap_count = 1` в `world.cpp`): после чтения
размеров он пропускает `(1−1)*W*H = 0` байт и читает `W*H` байт в `m_minimap_fov`,
затем `memcpy` в `m_minimap` (`World::ParseWrlFilePreview`,
`ResourceManager_InitInGameAssets` стр. 1196–1197). Двух отдельных слоёв (обычная +
fog-of-war миникарты) в файле нет.

Пример SNOW_1, первые 16 байт миникарты (смещение 0x0009):

```
63 63 64 64 64 63 69 64 64 63 64 63 63 64 64 64
```

Индексы 0x63–0x69 (99–105) — «водные» голубые цвета палитры (см. §1.5): край карты
SNOW_1 — океан. Гистограмма всей миникарты SNOW_1 (топ-8 индексов): 100 → 3 864 клетки,
99 → 3 733, 73 → 1 381, 105 → 965, 74 → 704, 68 → 625, 79 → 272, 139 → 104 — вода
(99/100/105) и «снежные» цвета суши (68–79, ср. пиксели тайла 0 в §1.4).

### 1.3. Карта tile-id (W·H × u16 LE)

Ровно `W*H` значений `uint16_t` little-endian, row-major (`index = y*W + x`), смещение
при штатных размерах `0x3109`. Значение в клетке — **номер тайла** (индекс в набор
тайлов из §1.4 и в pass-таблицу из §1.6). Отдельного TileType-перечисления нет:
id тайла — просто индекс.

Пример SNOW_1 (смещение 0x3109, первые 16 значений):

```
09 00 0A 00 0B 00 0B 00 0D 00 0E 00 0F 00 10 00 11 00 0A 00 0B 00 09 00 0A 00 0B 00 10 00 11 00
→ 9, 10, 11, 11, 13, 14, 15, 16, 17, 10, 11, 9, 10, 11, 16, 17
```

Проверено на всех 24 файлах: каждый id из диапазона `0..tile_count-1` встречается
хотя бы раз, максимальный id = `tile_count − 1`, ссылок за пределы набора (`>= tile_count`)
нет. (Единственное исключение — баг-фиксы порта в §3.3: SNOW_3 и SNOW_5 правит клетки,
но и там значения в файле корректны.)

### 1.4. Счётчик тайлов и пиксели тайлов

```
u16 LE tile_count           — число тайлов (штатно на 0x9309)
u8[tile_count × 64 × 64]    — пиксельные данные (штатно с 0x930B)
```

- Размер тайла — константа `GFX_MAP_TILE_SIZE = 64` (`gfx.hpp:28`): 64×64 = 4096 байт.
- Пиксель — 1 байт, **индекс палитры** файла (§1.5). Все 4096 пикселей значащие,
  прозрачного индекса нет: тайлы рисуются сплошняком (`Gfx_DecodeMapTile`,
  `gfx.cpp:125-199`, каждый пиксель пропускается через таблицу яркости). Порядок
  пикселей row-major.
- Тайлы идут **по порядку id**: сначала тайл 0, затем 1, … до `tile_count−1`.
  Сжатия нет (никакого RLE/LZSS).
- Режим «слабого железа» (`ResourceManager_DisableEnhancedGraphics`) — **не вариант
  файла**: порт читает из файла те же 64×64 и даунсамплит в 32×32 на лету
  (`World::LoadMapTiles`, `world.cpp:431-491`).
- Чтение порта кусками по `ceil(tile_count/8)` тайлов — деталь загрузчика (для
  прогресс-бара), на формат не влияет.

Пример SNOW_1, тайл 0, первые 64 байта (смещение 0x930B):

```
40 42 53 50 44 4A 49 44 49 4F 50 4A 4F 42 49 42 49 4A 49 42 40 42 42 50 57 54 42 44 50 42 4A 54
4E 4F 50 57 4A 44 44 44 4A 4F 4A 42 50 54 4F 4E 4A 4A 44 4A 42 44 42 4A 4E 4F 53 53 50 4A 57 53
```

(индексы 0x40–0x57 — «снежные» серо-голубые цвета).

### 1.5. Палитра (768 байт)

`256 × 3` байта: на каждый цвет 3 канала RGB, **8 бит на канал** (0–255). Смещение
(штатно) `0x930B + tile_count*4096`. Для SNOW_1 (tile_count=337) это `0x15A30B`,
первые 16 байт:

```
00 00 00 FF 00 00 D7 07 FF D7 07 FF FF FF 00 FF
→ цвет 0 = (0,0,0); цвет 1 = (255,0,0); цвета 2,3 = (215,7,255); цвет 4 = (255,255,0); …
```

Цвета 96–107 (водная гамма, индексы миникарты 0x62–0x69):

| idx | R | G | B | | idx | R | G | B |
|---|---|---|---|---|---|---|---|---|
| 96 | 79 | 127 | 163 | | 102 | 83 | 131 | 167 |
| 97 | 79 | 127 | 159 | | 103 | 79 | 119 | 155 |
| 98 | 79 | 127 | 163 | | 104 | 79 | 123 | 159 |
| 99 | 83 | 131 | 167 | | 105 | 83 | 127 | 163 |
| 100 | 87 | 135 | 171 | | 106 | 83 | 131 | 167 |
| 101 | 91 | 139 | 175 | | 107 | 87 | 135 | 171 |

- Палитра **пер-планетная**: сравнение GREEN_1 и SNOW_1 дало расхождения только в
  байтах 192–443, т.е. в записях 64–147; записи 0–63 и 148–255 у двух наборов совпали
  (общая часть палитры игры).
- Порт использует из WRL только записи 64–159: `World::LoadTilesAndMetadata`
  (`world.cpp:329-331`) делает `WindowManager_ColorPalette[i] = palette[i] / 4` для
  `i` в `[64*3, 160*3)`. Деление на 4 переводит 8-битные каналы файла во внутренний
  6-битный формат палитры порта (0–63) — та же конвенция, что у `COLOR.PAL`
  (`color.cpp:101`, `window_manager.cpp:590-592`). Базовые записи 0–63 и 160–255
  рабочей палитры берутся из `COLOR.PAL`, а не из WRL.
- Индексы этой палитры используют и миникарта (§1.2), и пиксели тайлов (§1.4).

### 1.6. Pass-таблица (tile_count байт)

`tile_count` байт, по одному на тайл (в порядке id). Значение — **индекс в массив
PassData** (0–3):

| Значение | Поверхность | SURFACE_TYPE_* |
|---|---|---|
| 0 | суша | `LAND` (0x1) |
| 1 | вода | `WATER` (0x2) |
| 2 | побережье | `COAST` (0x4) |
| 3 | «воздух» (непроходимо для наземного/водного, напр. вулкан/горы) | `AIR` (0x8) |

Смещение: `палитра + 768`. Гистограмма SNOW_1 (337 значений): 0 → 179, 1 → 9, 2 → 43,
3 → 106. Значения вне 0..3 в реальных файлах не встречаются (в C++ они дали бы чтение
за границей `PassData[4]` — см. §7).

Хвост pass-таблицы SNOW_1 (последние 8 байт файла, смещения 0x15A754–0x15A75B):

```
03 00 03 03 00 00 03 00
```

## 2. Hex-дампы заголовка (реальные файлы)

Первые 16 байт четырёх файлов; разметка: сигнатура(3) + layer_count(2) + dims[0](4) +
первые байты миникарты:

```
GREEN_1.WRL  57 52 4C 01 00 70 00 70 00 63 62 64 64 64 62 64   WRL...pp.ccddd b d
DESERT_1.WRL 57 52 4C 01 00 70 00 70 00 63 63 64 63 63 64 63   WRL...pp.ccdccdc
CRATER_1.WRL 57 52 4C 01 00 70 00 70 00 62 62 62 63 63 62 63   WRL...pp.bbbccbc
SNOW_1.WRL   44 4D 4F 01 00 70 00 70 00 63 63 64 64 64 63 69   DMO...pp.ccdddc i
```

- `57 52 4C` = `"WRL"`; у SNOW_1 — `44 4D 4F` = `"DMO"` (битая сигнатура, см. §1.1).
- `01 00` — layer_count = 1; `70 00 70 00` — dims[0] = (112, 112).
- Дальше (со смещения 0x0009) — байты миникарты: индексы палитры 0x62–0x69.

Смещения секций SNOW_1.WRL (tile_count = 337, размер 1 419 100 = 0x15A75C):

| Секция | Смещение | Размер | Конец |
|---|---|---|---|
| сигнатура | 0x000000 | 3 | 0x000003 |
| layer_count | 0x000003 | 2 | 0x000005 |
| dims[0] | 0x000005 | 4 | 0x000009 |
| миникарта | 0x000009 | 12 544 | 0x003109 |
| карта tile-id | 0x003109 | 25 088 | 0x009309 |
| tile_count | 0x009309 | 2 | 0x00930B |
| пиксели тайлов | 0x00930B | 337 × 4096 = 1 380 352 | 0x15A30B |
| палитра | 0x15A30B | 768 | 0x15A60B |
| pass-таблица | 0x15A60B | 337 | 0x15A75C (EOF) |

`tile_count` в SNOW_1 по смещению 0x9309: `51 01` = 337 (0x0151, LE).

## 3. Как из WRL получается SurfaceMap

### 3.1. Формула (pass-таблица)

Дословная семантика `World::LoadTilesAndMetadata`, `world.cpp:380-412`:

```c
const uint8_t PassData[] = {SURFACE_TYPE_LAND, SURFACE_TYPE_WATER,
                            SURFACE_TYPE_COAST, SURFACE_TYPE_AIR};  // {1, 2, 4, 8}
uint8_t pass_table[tile_count];
fread(pass_table, 1, tile_count, fp);              // сырые индексы 0..3 из файла
for (i = 0; i < tile_count; ++i)
    pass_table[i] = PassData[pass_table[i]];       // 0→LAND, 1→WATER, 2→COAST, 3→AIR
for (i = 0; i < W*H; ++i)
    surface_map[i] = pass_table[tile_ids[i]];      // surface = PassData[pass_table[tile_ids[i]]]
```

То есть для каждой клетки `i`: читается id тайла из карты tile-id, по нему — байт
pass-таблицы, байт трактуется как индекс в `PassData`. Результат — массив `W*H` байт
`surface_map[]`, где значение клетки — один из `SURFACE_TYPE_*` (битовая маска
проходимости):

```c
// enums.hpp:60-66
SURFACE_TYPE_NONE = 0x0,  SURFACE_TYPE_LAND = 0x1,  SURFACE_TYPE_WATER = 0x2,
SURFACE_TYPE_COAST = 0x4, SURFACE_TYPE_AIR = 0x8
```

Rust-порт — чистая функция `derive_surface_map` в `max-rust/crates/max_core/src/setup.rs:425`
(порт `world.cpp:382-409`):

```rust
pub const PASS_TABLE_SURFACES: [Surface; 4] = [Surface::LAND, Surface::WATER,
                                               Surface::COAST, Surface::AIR];
// setup.rs:63-67
pub fn derive_surface_map(tile_ids: &[u16], pass_table: &[u8]) -> SurfaceMap
```

`Surface` в Rust — битовая маска `NONE=0x00, LAND=0x01, WATER=0x02, COAST=0x04, AIR=0x08`
(`max-rust/crates/max_core/src/enums.rs:716-730`), размер карты —
`MAP_WIDTH = MAP_HEIGHT = 112`, `MAP_TILES = 12 544`
(`max-rust/crates/max_core/src/geo.rs:19-23`). Некорректные индексы (tile_id ≥
tile_count, pass-байт ≥ 4) в C++ — выход за границы массива; в Rust они дают
`Surface::NONE` + `debug_assert!` (см. §7).

### 3.2. Порядок применения в игре

1. `ResourceManager_InitInGameAssets(world)` (`resource_manager.cpp:1137`):
   `world_resource_id = SNOW_1 + world` — номер планеты 0..23 адресует ресурсы
   `SNOW_1..SNOW_6, CRATER_1..CRATER_6, GREEN_1..GREEN_6, DESERT_1..DESERT_6` по порядку.
2. Конструктор `World` — «предпросмотр» (`ParseWrlFilePreview`): читает заголовок,
   dims[0] и миникарту (§1.2); палитра и тайлы не читаются.
3. `World::LoadFullMap` (`world.cpp:93-172`): повторно открывает файл, читает карту
   tile-id (§1.3), пропускает tile_count, читает пиксели тайлов (§1.4), палитру (§1.5),
   строит `surface_map` (§3.1). `cargo_map` (ресурсы на клетках) при этом **обнуляется** —
   данные ресурсов в WRL отсутствуют.
4. `GameManager_InitMap` (`game_manager.cpp:1531`) файл уже не читает: он «применяет»
   загруженную карту — сбрасывает зум, отрисовывает вид, запускает первый тик и включает
   рендер (`GameManager_IsMapInitialized = true`).
5. Потребители поверхности: `Access_GetSurfaceType(grid_x, grid_y)` →
   `World::GetSurfaceType` (`world.cpp:1028-1038`) — возвращает байт surface_map
   (row-major `y*W + x`), вне границ и до загрузки — `SURFACE_TYPE_NONE`. По значению
   маски решается проходимость юнитов (`access.cpp`: вода/побережье для наземных,
   `MOBILE_LAND_UNIT`, субмарины и т.п.).

### 3.3. Известные дефекты данных и баг-фиксы порта

`World::ApplyBugFixes` (`world.cpp:559-915`) правит три файла, **только если SHA-256
файла совпадает с эталоном** (все три хеша совпали с реальными файлами — фиксы
применяются):

| Файл | SHA-256 (эталон в коде) | Что в файле | Что делает порт |
|---|---|---|---|
| `GREEN_4.WRL` | `dbcfc449…4605…` (полностью: `dbcfc4495334640776e6a0b1776651f904583aa87f193a43436e6b1f04635241`) | `pass_table[190] = 3` (→ AIR), а тайл — суша | всем клеткам с `tile_ids[i] == 190` ставит `SURFACE_TYPE_LAND` |
| `SNOW_3.WRL` | `a625d409ca1d5cd24cdeed165813e5b79c538b123491791016372492f5106801` | `tile_ids[56*112+56] = 32` (клетка 57,57 при 1-индексации) | заменяет id на 55 |
| `SNOW_5.WRL` | `11a9255e65af53b6438803d0aef4ca96ed9d57575da3cf13779838ccda25a6e9` | tile_count = 411; клетка (54,65) = 7 | инжектит 412-й тайл (id 411): 64×64 байт арта из кода, ставит клетку (54,65) → 411 и поверхность `AIR` |

## 4. Связь с RES, именами файлов и перечислениями

### 4.1. Ресурсы-ссылки в MAX.RES

Сами WRL-файлы в MAX.RES **не лежат**. В MAX.RES есть 24 записи-ссылки (11 байт
ASCIIZ каждая) с именами свободных файлов (см. `formats/res.md` §5; проверено
`tools/res_parser.py` на MAX.RES):

```
SNOW_1   = "snow_1.wrl\0"    (73 6E 6F 77 5F 31 2E 77 72 6C 00)
SNOW_2   = "snow_2.wrl\0"    … и так далее до
DESERT_6 = "desert_6.wrl\0"
```

- ID ресурсов: `SNOW_1 = 0x76E … SNOW_6 = 0x773`, `CRATER_1 = 0x774 … CRATER_6 = 0x779`,
  `GREEN_1 = 0x77A … GREEN_6 = 0x77F`, `DESERT_1 = 0x780 … DESERT_6 = 0x785`
  (`resourcetable.hpp:1931-1954`).
- Цепочка загрузки (`world.cpp:48-74`, `resource_manager.cpp:817-861`):
  `ResourceManager_ReadResource(id)` читает из MAX.RES ASCIIZ-имя файла; затем файл
  ищется на диске сначала в нижнем регистре (`snow_1.wrl`), при неудаче — в верхнем
  (`SNOW_1.WRL`) — так DOS-имена 8.3 работают на case-sensitive файловых системах.

### 4.2. Таблица планет (world 0..23 → файл)

`world_resource_id = SNOW_1 + world` (`resource_manager.cpp:1183`):

### 4.3. Enum-ы

- `SURFACE_TYPE_*` (§3.1) — единственный enum, связанный с WRL напрямую; значение
  клетки surface_map — битовая маска проходимости.

## 5. Псевдокод загрузчика

Порт эталона (`world.cpp`: `ParseWrlFilePreview` + `LoadFullMap` + `LoadTilesAndMetadata`),
порядок чтения 1:1 как в файле:

```
open(path)                                  # path = имя из MAX.RES, lower→upper-case
# --- предпросмотр (конструктор World) ---
seek(3)                                     # сигнатура НЕ проверяется
layer_count  = read_u16_le()
dims         = read(layer_count × {i16 x, i16 y})
W = dims[0].x;  H = dims[0].y;  cells = W*H
minimap_fov  = read(cells × u8)             # ровно один слой; он же minimap (memcpy)

# --- полная загрузка ---
seek(3); read_u16_le(); read(layer_count × Point)   # повторное чтение заголовка
skip(cells)                                 # пропуск уже прочитанной миникарты
tile_ids     = read(cells × u16_le)         # карта tile-id
tile_count   = read_u16_le()
tiles        = read(tile_count × 64×64 u8)  # пиксели тайлов по порядку id
palette      = read(256 × 3 × u8)           # 8 бит/канал
pass_table   = read(tile_count × u8)

# --- производные структуры ---
PassData = {LAND, WATER, COAST, AIR}        # {1, 2, 4, 8}
for i in 0..tile_count:  pass_table[i] = PassData[pass_table[i]]
for i in 0..cells:       surface_map[i] = pass_table[tile_ids[i]]
cargo_map[i] = 0                            # ресурсов в WRL нет

# --- применение ---
ColorPalette[64..160] = palette[64..160] / 4        # 8-бит → 6-бит
# доступ к поверхности: Access_GetSurfaceType(x, y) = surface_map[y*W + x],
# вне границ — SURFACE_TYPE_NONE
# при совпадении SHA-256 — ApplyBugFixes (GREEN_4 / SNOW_3 / SNOW_5), см. §3.3
```

## 6. Проверка парсера (инварианты реальных файлов)

Для всех 24 файлов выполняются инварианты (проверены по байтам):

1. размер = `38 411 + 4097*tile_count` (при `layer_count=1`, dims (112,112));
2. `dims[0] == (112, 112)`, `layer_count == 1`;
3. сигнатура — `"WRL"` у 23 файлов, `"DMO"` у SNOW_1 (на корректность не влияет);
4. все значения карты tile-id < tile_count; каждый id 0..tile_count−1 используется;
5. все байты pass-таблицы ∈ 0..3;
6. палитра: 256×3 байта, каналы 0..255; записи 0–63 и 148–255 совпадают между
   планетами, 64–147 — индивидуальны (проверено на паре GREEN_1/SNOW_1);
7. последний байт pass-таблицы — последний байт файла.

PowerShell-проверка (SNOW_1.WRL):

```powershell
$b=[System.IO.File]::ReadAllBytes('D:\dev\max-port-debug\max-original\SNOW_1.WRL')
$sig=[Text.Encoding]::ASCII.GetString($b,0,3)          # 'DMO'
$lc=[BitConverter]::ToUInt16($b,3)                     # 1
$x =[BitConverter]::ToInt16($b,5); $y=[BitConverter]::ToInt16($b,7)  # 112, 112
$cells=$x*$y; $tidOff=3+2+4*$lc+$cells                 # 12553 = 0x3109
$tc=[BitConverter]::ToUInt16($b,$tidOff+2*$cells)      # 337 @ 0x9309
$tilesOff=$tidOff+2*$cells+2                           # 0x930B
$palOff=$tilesOff+$tc*4096                             # 0x15A30B
$passOff=$palOff+768                                   # 0x15A60B
"sig=$sig layers=$lc dims=($x,$y) tc=$tc size=$($b.Length) end=$($passOff+$tc)"
# ожидается: sig=DMO layers=1 dims=(112,112) tc=337 size=1419100 end=1419100
```

## 7. Замечания для Rust max_assets

1. **Порядок байтов**: весь файл little-endian; структуры без паддинга. Читать поля
   по отдельности (`u16::from_le_bytes`, `i16::from_le_bytes`) — `#[repr(C, packed)]`
   не нужен.
2. **Сигнатуру не проверять строго** (или только предупреждать): порт пропускает 3 байта
   безусловно; `SNOW_1.WRL` имеет `"DMO"`. Отбраковывать файл по сигнатуре — ошибка.
3. **layer_count**: реальные файлы — всегда 1. C++-порт читает `layer_count` записей
   размеров в стековый массив на 12 — при `layer_count > 12` переполнение; в Rust читать
   в `Vec` с проверкой границ файла. Используется только `dims[0]`;
   `layer_count == 0` → `dims[0]` не существует → ошибка «файл повреждён».
4. **Размер карты не хардкодить**: формат допускает любые dims[0]; штатно 112×112.
   `MAP_TILES = 12 544` в `max_core` — константа геймплея, при парсинге WRL валидировать
   `dims[0] == (112,112)` или обрабатывать другие размеры явно.
5. **Миникарта**: ровно один слой `W*H` байт (порт читает один слой и копирует его в
   «обычную» и «FOV» миникарты). Число слоёв в файле, отличное от 1, в реальных данных
   не встречается; байты слоя — индексы палитры этого же файла.
6. **Границы индексов**: `tile_ids[i] >= tile_count` и `pass_byte >= 4` — в C++ чтение за
   границей массива (UB). В реальных файлах не встречается, но парсер должен это
   проверять; семантика Rust-порта: клетка/тайл получают `Surface::NONE` +
   `debug_assert!` (`derive_surface_map`, `setup.rs:425-453`).
7. **Нет сжатия**: тайлы — сырые 64×64 индексы палитры, миникарта/палитра/pass — сырые
   байты. Никакого RLE/LZSS/декомпрессии. `ResourceManager_DisableEnhancedGraphics`
   (32×32) — рантайм-даунсамплинг порта, не формат.
8. **Палитра 8-бит/канал**: внутренний формат игры — 6 бит (0–63), файл хранит 8-битные
   каналы; порт делит на 4 записи 64–159. Для рендера в max_assets хранить палитру как
   `[u8; 768]` и при необходимости применять `/4` для индексов 64..159 (остальные записи
   берутся из `COLOR.PAL`, не из WRL).
9. **Баг-фиксы порта** (§3.3) привязаны к SHA-256 файла; если max_assets воспроизводит
   поведение порта — реализовать те же три правки с той же проверкой хеша.
10. **Имена файлов**: из MAX.RES берётся ASCIIZ-имя в нижнем регистре; искать файл
    lower, затем upper (DOS 8.3). Список из 24 имён — §4.2.
11. **tile_count = 0** (теоретически): размер файла меньше секций — отсекать по формуле
    размера (§1) до чтения пикселей; `tile_count` читается как u16 — максимум 65 535
    тайлов ≈ 268 МБ, проверять `tiles_off + tc*4096 + 768 + tc <= file_len`.
12. **WRL ≠ сейв**: файлы `.DMO` (SAVE1.DMO и т.п.) — SmartFile версии 70 (первые байты
    `46 00` = 70, затем имя объекта `"demo\0"`), а не карты; несмотря на совпадение
    «сигнатуры» SNOW_1.WRL с расширением `.DMO`, парсить DMO как WRL нельзя.
13. **Эталон для тестов**: инварианты и смещения §6 на SNOW_1.WRL (tile_count=337) и
    GREEN_1.WRL (tile_count=271, палитра @ 0x11830B); сверять формулу размера на всех
    24 файлах из таблицы в шапке.
