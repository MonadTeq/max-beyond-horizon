# Организация тестирования (правила по ролям)

Канонические правила размещения и приёмки тестов. Инструментарий: `cargo test` +
`cargo-nextest` + `rstest` + (опционально) `insta`. Версия 0.1 · 2026-11-25.

## Ключевой принцип

**Тесты не живут в файлах бизнес-логики, кроме unit-тестов.** Разделение
ответственности: unit-тесты — рядом с приватной логикой, интеграционные — через
публичный API в `tests/`, golden/CRC — в `max-brh-qa/`. Тест в файле логики означает
тестовый код в продакшн-крейте и маскировку регрессий при рефакторинге.

## Где живут тесты (по типу)

| Тип | Расположение | Что проверяет |
|---|---|---|
| unit | `#[cfg(test)] mod tests` в том же `src/*.rs` | приватные функции/инварианты, недоступные через публичный API |
| интеграционный | `tests/*.rs` крейта, **не** в `src/` | публичный API, сценарий (`GameUniverse`, сеть, save/load) |
| golden/CRC | `max-brh-qa/` или `tests/golden/`, **не** в `src/` | визуал 1:1, дайджесты |
| property-based | `tests/` или `#[cfg(test)]` с пометкой «свойство» | инварианты (round-trip, детерминизм, эквивалентность каналов) |

## Требования по ролям

### Аналитик
- **A1.** В ТЗ для каждого блока указать: unit-тесты (и в каком модуле), интеграционные
  (и в каком `tests/*.rs`), golden/CRC (и нужно ли обновлять эталоны — с обоснованием),
  property-based (какие инварианты).
- **A2.** Формулирует **свойство**, не инструмент: «старт из реестра эквивалентен прямому
  по `snapshot_bytes`», «save/load round-trip байт-в-байт». Инструмент — за Разработчиком.
- **A3.** Для каждого теста — критерий приёмки: «тест X доказывает свойство Y; при
  регрессе падает с сообщением Z».
- **A4.** Флакающие (тайминг/сеть) — отдельная категория: «требует `--retries`/`GATE_LOCK`».
- **A5.** Запрет на «тесты ради покрытия»: нет свойства — нет теста.

### Архитектор
- **Ar1.** Утверждает структуру: unit в `src/`, интеграционные в `tests/`, golden в `qa/`.
- **Ar2.** Публичный API — единственная точка входа интеграционных тестов; запрос
  `universe_mut()` — сигнал нехватки API, а не повод добавить `pub` (регрессия C3).
- **Ar3.** `cargo-nextest` — стандарт CI (с `--retries`), не `cargo test`.
- **Ar4.** `rstest` — только для табличных случаев/общих фикстур.
- **Ar5.** `insta` — опционально, только для новых снапшотов без golden-инфраструктуры,
  с пометкой «почему не golden».
- **Ar6.** Запрет на интеграционные тесты в `src/` (GameUniverse/сеть/save-load).

### QA
- **Q1.** Приёмка теста по критерию, не по «зелёному»: тест падает при регрессе?
- **Q2.** Аудит разделения grep'ом: `src/` — только `#[cfg(test)]` unit; `tests/` —
  интеграционные; `max-brh-qa/` — golden.
- **Q3.** Флаки — триаж как golden-triage; изолированно проходит → `--retries`/`GATE_LOCK`.
- **Q4.** CI на nextest? `--retries` настроен? JUnit XML генерируется?
- **Q5.** Golden/CRC — эталоны обновляются только с записью в `golden-triage.md`.
- **Q6.** На ревью: тест проверяет свойство или «вызвать и не упасть»?

### Разработчик
- **D1.** Тест в правильном месте по типу (таблица выше).
- **D2.** `#[test]` в `src/foo.rs` — только внутри `#[cfg(test)] mod tests`.
- **D3.** `cargo nextest run` локально и в CI; `cargo test` — для doctest.
- **D4.** `rstest` — только `#[case]`/`#[fixture]`.
- **D5.** `insta` — только с одобрения Архитектора, `cargo insta review`.
- **D6.** Флаки не замазывать: без `#[ignore]` без записи в backlog; без «таймаут до
  бесконечности»; формулировать «тайминг-чувствителен → retries/GATE_LOCK или переписать».
- **D7.** Compile-time assert для констант-«замков» (`const { assert!(!X) }`) — регрессия
  ловится на сборке.
- **D8.** Сообщение падения объясняет свойство: `assert_eq!(a, b, "registry start must
  equal direct start by snapshot_bytes; see ADR-...")`.
- **D9.** Без `#[cfg(test)]`-веток в продакшн-путях.
- **D10.** Ревью-чеклист перед коммитом: место? свойство? падает при регрессе? флакает?
  сообщение объясняет?

## Процессное правило (владелец)

Правило зафиксировано здесь и в `AGENTS.md`. **Аудит накопленных тестов** (перенос
интеграционных из `src/` в `tests/`) — в backlog, приоритет «при касании модулей».
