# План: сетевой режим хоста (P2P) — цель 2

Версия: 0.1 (черновик) · 2026-11-21

## 1. Цель и границы

Вернуть сетевую игру **в режиме хоста**, как в оригинале: один из игроков
является хостом (ENet-сервер, авторитет сессии), остальные подключаются к нему
напрямую по TCP/IP. Это цель 2 и 2.1 архитектурного плана клиента
(`max-brh-docs/architecture/client/README.md`).

Границы:

- **Не** заменяет выделенный сервер (Horizon): хост-режим — отдельный,
  локальный способ организации партии; выделенный сервер остаётся для
  постоянных/публичных игр.
- Речь идёт о клиентской сети (P2P между клиентами), а не о headless-арбитре.
- Механика игры и lockstep-симуляция не меняются: переиспользуются
  `max_core` (симуляция) и `max_net` (ENet + пакеты).

## 2. Исходное состояние

### 2.1 Оригинал (M.A.X. Port)

- Партия — P2P-меш поверх ENet; первый пир принимает роль ENet-сервера
  (`server role`), остальные подключаются к его адресу (`remote.cpp`,
  `transport_udp_default.cpp`).
- Синхронизация — детерминированный lockstep: по сети идут только приказы/
  события и барьеры (00/52/45/54), а не состояние. См.
  `architecture/client/barrier-flow.md`, `architecture/client/protocol.md`.

### 2.2 Текущее состояние (BRH)

- Сетевая игра реализована через **выделенный сервер**: клиент → Horizon
  (gRPC/WS-лобби) → headless-арбитр (`max-port --server`), топология «звезда»
  (клиенты ↔ арбитр). Хост-режим отсутствует.
- В меню уже есть точки входа `Host Network Game` / `Join Network Game`
  (`Multiplayer Menu`, `plan-modes.md` M-HS) — сейчас обе открывают форму
  создания/список игр Horizon. Их предстоит развести на «хост» (локальный) и
  «подключение» (к хосту), либо дополнить пунктами.

## 3. Этапы

### Этап 1. Локальный хост-режим (M-NET-HOST)

Клиент поднимает сессию без Horizon: сам становится ENet-сервером и арбитром
партии.

- [ ] ENet-сервер внутри клиента: `max_net` принимает роль сервера
  (`server role` первого пира), назначает порт, раздаёт слоты команд.
- [ ] Арбитр-роль хоста: хост выполняет барьерную синхронизацию и CRC-проверки
  (функции, которые в выделенном режиме делает `max-port --server`).
- [ ] UI: `Host Network Game` → локальная форма (карта/правила/слоты) → ожидание
  подключения, без обращения к Horizon.

Критерий: на одном ПК поднимается сессия-хост, партия стартует и проходит N
ходов против ИИ (без гостей).

### Этап 2. Подключение гостя (M-NET-JOIN)

Второй клиент подключается к хосту напрямую.

- [ ] `Join Network Game` → ввод адреса хоста (IP:port) вместо списка Horizon.
- [ ] ENet-клиент к хосту: подключение, приветствие/рукопожатие, вход в
  lockstep-сессию (пакеты `TP 00`/барьеры как в существующем стеке).
- [ ] Синхронизация состава команд и стартовых настроек между хостом и гостем.

Критерий: 2 клиента на разных машинах проходят 10 ходов партии (приказы,
барьеры без таймаутов, CRC совпадает).

### Этап 3. Паритет и надёжность (M-NET-HOST-POLISH)

- [ ] Обрыв связи: повторное подключение и продолжение партии (resume-54,
  реконнект) в хост-режиме.
- [ ] Более 2 игроков (2–4) в меше/звезде хоста.
- [ ] Детерминизм: replay/CRC партии хост-режима совпадает с эталоном C++.
- [ ] Тесты: UNIT (`max_net` хост/гость, барьеры), интеграционные (2 клиента),
  live-smoke на реальном стенде.

## 4. Верификация

- UNIT: `max_net`/`max_core` — роль сервера/клиента, рукопожатие, барьеры,
  реконнект.
- QA-сценарий `host-join.qa` (2 клиента, 10 ходов) + golden-кадры.
- live-smoke: `live-smoke.sh` переведён/продублирован на хост-режим (без
  Horizon, прямой адрес).
- Соответствие C++: порядок пакетов и барьеров — по
  `architecture/client/protocol.md` и `architecture/client/barrier-flow.md`.

## 5. Зависимости и риски

- Зависимость: существующий стек `max_net` (ENet + пакеты) и арбитр-логика уже
  есть в выделенном режиме — этап 1 переносит их в клиент, а не пишет заново.
- Риск: «звезда хоста» против «меша» оригинала. Оригинал — меш; первым шагом
  допустима звезда через хост (как в выделенном режиме), меш — при
  необходимости позже.
- Риск: конфликт ролей «клиент и арбитр в одном процессе». Решается выделением
  арбитр-функций в отдельный слой, вызываемый из клиентского процесса.
