# Правила программирования на Rust

Канонические правила реализации игры на Rust. Заполняются по мере объяснения и
уточнения; дополнения и исправления — только через владельца правил (человека).

**Обязательность:** агент-программист следует этим правилам строго. Если правило
не покрывает ситуацию или в нём есть неопределённость — агент **останавливается
и задаёт уточняющий вопрос**, а не домысливает.

## Порядок работы с правилами

1. Владелец формулирует правило.
2. Агент фиксирует понимание, задаёт уточняющие вопросы при неоднозначности.
3. Правило записывается в этот документ с примером/ссылкой на код.
4. Программист применяет правило; при неуверенности — останавливается и спрашивает.

## Правила

### Правило 1. Чистая Rust-архитектура: enum для классификации, traits для поведения

**Формулировка.** Архитектура и код следуют стандартам сообщества Rust. Наследование
«is-a» (как в C#/Java) **не используется**; вместо него — композиция данных
(«has-a») и типажи («can-do»). Классификатор выражается через `enum`; поведение —
через `trait`; иерархия признаков — через маркерные типажи и композицию.

**Согласование с бит-в-бит паритетом (уточнено владельцем).** Битовые флаги,
совместимые с C++ (`MOBILE_AIR_UNIT`, `MOBILE_LAND_UNIT`, `STATIONARY`,
`GROUND_COVER`, `CONNECTOR_UNIT`, `HOVERING` и т.д.), остаются **только** в
сериализуемом состоянии (снапшот/CRC) ради бит-в-бит паритета с оракулом.
Поверх них строится **типобезопасный слой**: `enum` для классификации и
маркерные типажи как «вид» на эти флаги. Логика и поведение пишутся через
типажи, а **не** через прямые проверки битов.

**Правила применения.**

1. Сущность классифицируется `enum` (например `UnitType`, `Order`,
   `OrderState`), а не флагами-строками и не иерархией классов.
2. Способности и поведение — `trait` (`CanMove`, `CanAttack`, `CanBuild`,
   `IsAirUnit`, `IsStationary`…); маркерные типажи — для признаков без данных.
3. Состояние, влияющее на детерминизм (флаги C++), хранится как данные и
   сериализуется бит-в-бит; типобезопасный вид — отдельный слой над ним.
4. Проверки поведения в логике — через типажи/методы, а не через `if
   flags & MOBILE_AIR_UNIT != 0`.

**Цель.** Лёгкий, читаемый, поддерживаемый и, главное, тестируемый код: чистые
функции и типажи проще изолировать и покрыть тестами, чем иерархии и битовые
ветвления.

### Правило 2. Чистое решение вместо копирования нечистого кода оракула

**Формулировка.** Если прямое решение задачи (в лоб) заставляет переносить из
оригинала или C++-оракула нечистый или ошибочный код, задача решается заново —
**в чистом коде и нашей архитектуре**. Копирование нечистого кода вместе с его
багами не допускается. Компромиссы по качеству кода не принимаются; спешка не
допускается.

**Граница (уточнена владельцем).**

- Чистое решение **сохраняет наблюдаемое поведение 1:1**: игровые механики,
  визуал и детерминизм (снапшот/CRC) остаются совместимыми с C++-оракулом.
- Меняется **только внутренняя структура**: как задача реализована в коде, а не
  то, что она делает.
- Известные **поведенческие ошибки оригинала** исправляются **отдельно**, в
  рамках цели 3.1 («Исправление известных ошибок оригинала»), с явной пометкой
  расхождения и обновлением эталонов CRC/sim-векторов. Чистый рефакторинг
  поведение менять не должен.

**Применение.**

1. Сначала изучить, как задача решена в C++-оракуле.
2. Если перенос «в лоб» воспроизводит нечистую структуру или баги — спроектировать
   чистое решение в нашей архитектуре (enum + traits, композиция, без битовых
   ветвлений в логике — правило 1).
3. Сверить наблюдаемое поведение и детерминизм с оракулом; расхождение поведения
   без решения владельца не допускается.
4. Поведенческую ошибку оригинала — не исправлять «по пути»; оформить отдельной
   задачей по цели 3.1.

**Цель.** Не переносить в проект чужой нечистый код и его дефекты; при этом
паритет с оригиналом сохраняется как внешнее, наблюдаемое свойство.
