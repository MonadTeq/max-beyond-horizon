# Правила программирования на Rust

Канонические правила реализации игры на Rust. Заполняются по мере объяснения и
уточнения; дополнения и исправления — только через владельца правил (человека).

**Обязательность:** агент-программист следует этим правилам строго. Если правило
не покрывает ситуацию или в нём есть неопределённость — агент **останавливается
и задаёт уточняющий вопрос**, а не домысливает.

## Порядок работы с правилами

1. Владелец формулирует правило.
2. Агент фиксирует понимание, задаёт уточняющие вопросы при неоднозначности.
3. Правило записывается в этот документ с примером/ссылкой на код.
4. Программист применяет правило; при неуверенности — останавливается и спрашивает.

## Правила

### Правило 1. Чистая Rust-архитектура: enum для классификации, поведенческие traits для поведения

**Формулировка.** Архитектура и код следуют стандартам сообщества Rust. Наследование
«is-a» (как в C#/Java) **не используется**; вместо него — композиция данных
(«has-a») и поведенческие типажи («can-do»). Классификация — через **`enum`**;
поведение — через **поведенческие `trait` с методами** (`CanMove`, `CanAttack`,
`CanBuild`).

**Маркерные типажи без реализаций НЕ используются** (решение владельца, вариант C):
для закрытого множества `enum` (93 варианта `UnitType`) классификацию несёт
`enum` (единственный источник истины), а не маркерные типажи — `impl Combat for
UnitType` означал бы «боевой» у всех 93 и был бы мёртвым кодом. Проверка
категории — через `match`/`matches!` по значению enum (`CombatRole::classify`).

**Согласование с бит-в-бит паритетом (уточнено владельцем).** Битовые флаги,
совместимые с C++ (`MOBILE_AIR_UNIT`, `MOBILE_LAND_UNIT`, `STATIONARY`,
`GROUND_COVER`, `CONNECTOR_UNIT`, `HOVERING` и т.д.), остаются **только** в
сериализуемом состоянии (снапшот/CRC) ради бит-в-бит паритета с оракулом.
Поверх них строится **типобезопасный слой**: классифицирующие `enum`
(`CombatRole`, `Mobility`, `Environment`, `CargoKind`) как «вид» на эти флаги.
Логика и поведение пишутся через `enum`-методы и поведенческие типажи, а **не**
через прямые проверки битов.

**Правила применения.**

1. Сущность классифицируется `enum` (например `UnitType`, `Order`,
   `OrderState`), а не флагами-строками и не иерархией классов.
2. Поведение — поведенческие `trait` с методами (`CanMove`, `CanAttack`,
   `CanBuild`); ограничения обобщённого кода используют эти типажи
   (`fn f<T: CanMove>(…)`), а не маркеры категорий.
3. Принадлежность категории проверяется через `match`/`matches!` по значению
   enum, а не через ограничение типажа.
4. Состояние, влияющее на детерминизм (флаги C++), хранится как данные и
   сериализуется бит-в-бит; типобезопасный вид — отдельный слой над ним.
5. Проверки поведения в логике — через типажи/методы, а не через `if
   flags & MOBILE_AIR_UNIT != 0`.

**Цель.** Лёгкий, читаемый, поддерживаемый и, главное, тестируемый код: `enum`
закрывает классификацию, поведенческие типажи — обобщения; без мёртвого кода и
без лишних обёрток.

### Правило 2. Чистое решение вместо копирования нечистого кода оракула

**Формулировка.** Если прямое решение задачи (в лоб) заставляет переносить из
оракулов (Оракула Klei или Оракула Interplay) нечистый или ошибочный код, задача
решается заново — **в чистом коде и нашей архитектуре**. Копирование нечистого
кода вместе с его багами не допускается. Компромиссы по качеству кода не
принимаются; спешка не
допускается.

**Граница (уточнена владельцем).**

- Чистое решение **сохраняет наблюдаемое поведение 1:1** с Оракулом Interplay
  (оригинальная игра): игровые механики, визуал и детерминизм (снапшот/CRC)
  совместимы с оригиналом. «Отсебятина» Оракула Klei (отклонения от оригинала)
  **не переносится**.
- Меняется **только внутренняя структура**: как задача реализована в коде, а не
  то, что она делает.
- Известные **поведенческие ошибки Interplay** исправляются **отдельно**, в
  рамках цели 3.1 («Исправление известных ошибок оригинала»), с явной пометкой
  расхождения и обновлением эталонов CRC/sim-векторов. Чистый рефакторинг
  поведение менять не должен.

**Применение.**

1. Сначала изучить, как задача решена в Оракуле Klei (структура/имена/логика),
   затем сверить фактическое поведение с Оракулом Interplay.
2. Если перенос «в лоб» воспроизводит нечистую структуру или баги — спроектировать
   чистое решение в нашей архитектуре (enum + traits, композиция, без битовых
   ветвлений в логике — правило 1).
3. Сверить наблюдаемое поведение и детерминизм с оракулом; расхождение поведения
   без решения владельца не допускается.
4. Поведенческую ошибку оригинала — не исправлять «по пути»; оформить отдельной
   задачей по цели 3.1.

**Цель.** Не переносить в проект чужой нечистый код и его дефекты; при этом
паритет с оригиналом сохраняется как внешнее, наблюдаемое свойство.

### Правило 3. Приоритет оракулов и порядок разрешения нестыковок

**Формулировка.** Истина о поведении игры — **Оракул Interplay** (оригинальная
M.A.X. + дизассемблер: `max-original/` + `max-original-dasm/`). **Оракул Klei**
(C++-порт M.A.X. Port: `max-cpp-port/`) — вторичный референс по структуре,
именам и логике, но часто содержит «отсебятину» — отклонения от оригинала.
Нестыковка между ними разрешается в пользу Оракула Interplay.

**Порядок приоритетов.** Оракул Interplay → Оракул Klei → человек.

**Порядок действий при нестыковке.**

1. Зафиксировать нестыковку «Оракул Klei ↔ Оракул Interplay».
2. Верифицировать фактическое поведение по Оракулу Interplay (оригинал +
   дизассемблер, RE).
3. Interplay однозначен → истина = Interplay; отклонение Klei помечается как
   «отсебятина Klei» и **не переносится** (даже если оно «удобнее»).
4. Interplay неоднозначен или данных мало → **вопрос человеку**, ожидание
   решения; самостоятельно выбирать трактовку не допускается.

**Применение.** Не домысливать неоднозначное поведение; остановиться и следовать
порядку. Решение человека фиксируется в документации (правило или замечание к
задаче), чтобы не переспрашивать повторно.

### Правило 4. Разделение слоёв представления и прикладной логики

**Формулировка.** Слой представления (presentation) и слой прикладной логики
(application) разделяются строго. **Прикладной слой никогда не зависит от слоя
представления.** Это строжайшее правило; его нарушение не допускается ни при
каких условиях.

**Соответствие крейтам.**

- Прикладной слой (не зависит от представления): `max_core` (детерминированная
  симуляция, чистые функции без I/O), `max_net` (протоколы), `max_assets`
  (форматы ресурсов).
- Слой представления (зависит от прикладного, но не наоборот): `max_render`
  (отрисовка), `max_app` (UI/цикл/оркестрация).

**Правила применения.**

1. Зависимости направлены в одну сторону: представление → прикладной слой;
   обратная зависимость запрещена.
2. Прикладной слой не содержит ссылок на `max_render`/`max_app`, не импортирует
   типы/код представления.
3. Данные, нужные представлению, прикладной слой предоставляет через чистые
   данные/события, а не через вызовы вверх.
4. Любое изменение, вводящее зависимость прикладного слоя от представления, —
   ошибка, исправляется немедленно.

**Цель.** Прикладная логика остаётся независимой, детерминированной и
тестируемой без GUI/отрисовки; представление можно заменять, не затрагивая
логику.

### Правило 5. Строгая слоёная логика: UI → Application → Infrastructure

**Формулировка.** Разработка следует строгой слоёной структуре из трёх слоёв, с
зависимостями **только вниз**:

```
UI  →  Application  →  Infrastructure
```

Слой выше зависит от слоёв ниже; обратная зависимость запрещена.

**Соответствие крейтам.**

- **UI (представление):** `max_app` (цикл/UI/оркестрация), `max_render` (отрисовка).
- **Application (прикладная логика):** `max_core` (детерминированная симуляция).
- **Infrastructure (фундамент):** `max_net` (сетевой транспорт/протокол),
  `max_assets` (форматы ресурсов).

**Правила применения.**

1. `max_app`/`max_render` зависят от `max_core`, `max_net`, `max_assets`; не наоборот.
2. `max_core` зависит от Infrastructure (`max_assets`/`max_net`), если требуется,
   и **никогда** от UI (правило 4).
3. `max_net`/`max_assets` не зависят от слоёв выше (UI/Application) и между собой
   без необходимости.
4. Новый код помещается в тот слой, которому он принадлежит; зависимость через
   границу вверх — ошибка, исправляется немедленно.

**Цель.** Один направленный граф зависимостей: каждый слой тестируется и
заменяется независимо; UI можно менять, не затрагивая Application и
Infrastructure.

### Правило 6. Доменный язык (DSL) и трассировка к оракулу

**Формулировка.** Имена объектов кода образуют единый доменный язык (DSL),
используемый аналитиками, дизайнерами, программистами и архитекторами.
Публичные имена — идиоматичные и доменно-чистые. Трассировка к оракулам
выполняется **системно, но не через имя**:

1. **Технический комментарий в коде** — doc-комментарий у каждой сущности,
   портированной из C++: `/// C++: <наша сущность> ↔ <C++-идентификатор>,
   <файл>:<строка>.` (например `Order::Build ↔ ORDER_BUILD,
   units_manager.cpp:2875`).
2. **Каноническая таблица `domain-map.md`** — соответствие
   «домен-термин → Rust-имя → C++-идентификатор → источник → примечание».

**Приоритет трассировки — средний (решение владельца):** имя остаётся чистым
(правила 1–2), трассировка обязательна и проверяема, но размещается в
комментарии и таблице, а не в имени.

**Правила применения.**

1. Публичный DSL использует идиоматичные доменные имена (не C++-аббревиатуры и
   не имена `UnitInfo`/`ORDER_BUILD` в качестве Rust-имён).
2. Каждая сущность, соответствующая C++, несёт doc-комментарий с C++-ссылкой;
   отсутствие ссылки — недочёт.
3. `domain-map.md` пополняется при введении каждой новой сущности; таблица —
   источник для сверки и для всех ролей.
4. Теги/строки из ресурсов игры (`MININGST`, `POWGEN`, …) — это данные
   (совместимость с файлами), а не имена типов; в коде они значения enum
   (`UnitType::MiningStation` с `fn tag()` → `"MININGST"`).

**Цель.** Один язык домена для всех ролей; чистота кода (правила 1–2);
трассировка к оракулу не теряется.

### Правило 7. Имена — максимально по стандартам Rust

**Формулировка.** Имена объектов кода следуют официальным соглашениям Rust
(RFC 0430, rustfmt, clippy) максимально, без собственных стилей.

**Соглашения.**

- Типы, перечисления, типажи, варианты перечислений — `UpperCamelCase`
  (`Unit`, `UnitType::MiningStation`, `Order::Build`, `AirUnit`).
- Функции, методы, переменные, поля, модули — `snake_case`
  (`build_time`, `grid_x`, `process_order_build`).
- Константы и статики — `SCREAMING_SNAKE_CASE` (`MAX_PORT_RANGE`,
  `AI_SAFE_ENEMY_DISTANCE`).
- Маркерные типажи — существительное/прилагательное без префиксов `Is`/`Has`
  (`AirUnit`, `Stationary`, `Hovering`), по образцу `Copy`/`Send`/`Sync`;
  поведенческие типажи — по образцу std (`Display`, `Iterator`, `IntoIterator`)
  либо глагольная способность без систематического префикса.

**Инструменты.** Код обязан проходить:

- `cargo fmt --check` — без изменений форматирования;
- `cargo clippy` — без предупреждений (дефолтный набор линтов).

**Применение.** Имена в публичном DSL и в `domain-map.md` — те же, что в коде
(одна форма для всех ролей); C++-имена фиксируются только в столбце «C++» и в
doc-комментариях (правило 6).

### Правило 8. Разработчик консультируется с аналитиком и архитектором

**Формулировка.** При написании кода, когда есть **серьёзные сомнения**,
разработчик консультируется с соответствующими ролями:

- **с аналитиком** — по доменному языку, именам и соответствиям «оригинал → DSL»
  (аналитик владеет `domain-map.md`, правило аналитика 1);
- **с архитектором** — по слоям, границам и контекстам (правило архитектора 1).

Если после консультации сомнение остаётся — эскалация к человеку (правило 3 для
спорных моментов оракула; правило архитектора 2 — по аналогии для кода).

**Правила применения.**

1. Сомнение в **имени/домене** → к аналитику; сомнение в **слое/границе** → к
   архитектору.
2. Неуверенность не «замалчивается» и не решается молчаливым выбором.
3. Результат консультации фиксируется (в коде doc-комментарием, в
   `domain-map.md` или в документации), чтобы не переспрашивать повторно.

**Цель.** Вопросы кода решаются в правильном контексте: домен — с аналитиком,
архитектура — с архитектором; без единоличных неуверенных решений.
