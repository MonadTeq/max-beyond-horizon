# Хранение и загрузка ресурсов (с учётом будущего ремастера)

Версия 0.1 · 2026-11-25. Состояние: обсуждение (не ADR), после измерений — Архитектору.

## Текущее состояние

- `MAX.RES` ≈ **17 МБ** (спрайты/палитры/WRL/текст), `PATCHES.RES` (дескрипторы `SC_*`);
  медиа отдельно: `MAXINT.MVE` **68 МБ**, музыка `*.MSC` по ~16 МБ.
- `ResArchive::open()` читает `.RES` целиком в `Vec<u8>` (owned), `read(name)` → `&[u8]`;
  декодирование ленивое (спрайт/палитра по первому обращению).

## Принципы

1. **Оракул неизменен.** `.RES`/`PATCHES.RES` — оракул; не модифицируются, не embed'ятся.
   Любой производный артефакт (индекс/кэш/ремастер-текстуры) — **удаляемый кэш** в
   `target/`/`build/`, не в репозитории, не замена оракула.
2. **Измерения прежде оптимизации.** Утверждения о производительности — только с
   цифрами или ссылкой на оракул, иначе «гипотеза» (analyst-rules.md Правило 3).
   Конкретно: «mmap быстрее `Vec` для 17 МБ» — **гипотеза до замера** (Vec быстрее на
   <2 МБ, mmap на >32 МБ, 17 МБ — между ними).
3. **Медиа — стриминг.** 68 МБ MVE и ~16 МБ MSC не грузить целиком; читать потоком.
4. **Не строить инфраструктуру под гипотетическую проблему.** Build-time индекс — только
   если профиль покажет, что старт реально медленный.

## Фаза 0 — измерения (первым шагом)

Замерить: время `ResArchive::open()` на 17 МБ; пик памяти; время первого декода спрайта;
время/память загрузки MVE и MSC. По результатам решить, нужна ли оптимизация ядра
`.RES` или достаточно стриминга медиа.

## Фаза 1 — по результатам измерений

- **Стриминг MVE/MSC** — реальный выигрыш (68 МБ + 16 МБ не в RAM).
- **mmap для `.RES`** — только если замер подтвердит выигрыш; `memmap2` = `unsafe`,
  требует явного инварианта «файл не изменяется во время работы» (оракул read-only).

## Фаза 2 (условно) — build-time индекс

Только если есть проблема, которую решает. Производный кэш (manifest + offset'ы +
декод-подсказки) в `target/`/`build/`, не в репозитории.

## Ремастер (будущее): KTX2 + Basis Universal

Цель — улучшенное качество ресурсов без потери производительности и без нарушения
принципа «оракул неизменен».

- **Формат текстур:** `KTX2` + полезная нагрузка **Basis Universal** (стандарт Khronos).
  Один `.ktx2` на текстуру → транскодируется на лету в нативный GPU-формат платформы
  (BC7 на десктопе, ASTC на мобилке, ETC2 на старых устройствах) — без тройных сборок.
- **Кодеки:** **UASTC** (почти без потерь при транскоде в BC7/ASTC) для героев/UI/
  карт нормалей; **ETC1S** (компактнее JPEG) для фонов.
- **Пайплайн (производный, оракул нетронут):**
  1. Исходники художников — lossless (PNG/TGA/PSD), без предварительного JPEG-сжатия
     (иначе «многослойные» артефакты).
  2. Build-time инструмент: `basisu` → `.ktx2`, в CI.
  3. Run-time: Rust-крейт (`libktx` полный / лёгкий `basis_universal` транскодер) читает
     `.ktx2` и транскодирует под GPU.
  4. Оригинальный `MAX.RES` остаётся на диске (эталон/обратная совместимость); ремастер
     подменяет пути текстур в своём манифесте (аналог `PATCHES.RES`).
- **Звук (`.MSC`)** — остаться на стриминге (Opus/OGG), KTX2 — только про GPU-текстуры.

## Развилки (требуют решения после Фазы 0)

1. Объём оптимизации ядра `.RES` — по замерам.
2. Ремастер: подтвердить KTX2+Basis как целевой формат; выбрать Rust-крейт
   транскодирования под текущий рендер-стек (SDL3/OpenGL/Vulkan).
3. Порядок: сначала Фаза 0 (измерения), потом решение по Фазе 1; ремастер-пайплайн —
   отдельный трек.
