# R0 — измерения и выбор транскодера (HD-ремастер)

Версия 1.0 · 2026-11-26 · Разработчик · трек `development/remaster-hd.md` §R0.

Гейт R0: отчёт измерений (память рендера, объём ассетов, транскодер) + `cargo test`
+ golden 1:1 зелёные. **Прод-код не менялся** — добавлены только инструмент
измерений (`max-brh-qa-tools/r0-measure/`) и этот отчёт.

Машина измерений: Intel Core i9-9900K (8 ядер / 16 потоков, 3.6 ГГц), 128 ГБ RAM,
NVIDIA RTX 3080 Ti (12 ГБ), Windows 10 Pro, rustc 1.94.0
(x86_64-pc-windows-msvc), MSVC 14.51, CMake 4.5.1. Все числа — из одного и того же
`max-original/MAX.RES` (1828 записей) и 24 карт `*.WRL`.

Воспроизведение:

```sh
cd max-brh-qa-tools/r0-measure
cargo run --release -- vram      --root ../..
cargo run --release -- inventory --root ../..
cargo run --release -- transcode --root ../.. --iterations 30
```

## 1. VRAM текущего режима 640×480

### 1.1 Кадровый путь (на кадр)

| буфер | объём |
|---|---:|
| кадр RGBA 640×480 (`RgbaBuffer`, `max_render`) | **1 228 800 B = 1,17 MiB** |
| текстура SDL (RGBA32 640×480, `create_texture_streaming` на каждый `present`) | **1 228 800 B** (GPU) |
| drawable окна (пиксели вывода × 4 B) | 640×480 → 1,17 MiB; 1280×960 → 4,69; 1920×1080 → 7,91; 2560×1920 → 18,75; 3840×2160 → 31,64 MiB |

Рендер-проход **не аллоцирует** (0 B за кадр): буфер кадра переиспользуется,
рисование идёт записью в него. Текстура пересоздаётся в
`SdlWindow::present` каждый кадр, поэтому резидентна ровно одна 640×480 RGBA.

Итого GPU при окне 1:1 — **2,34 MiB** (drawable + текстура); при окне 1920×1080 —
**9,08 MiB**; при 4K — **32,81 MiB**.

### 1.2 Рабочий набор рендера (CPU, heap-замер)

Замер `Assets::load` — тем же вызовом, что делает клиент (headless): **75,17 MiB**,
0,11 с, пик +75,18 MiB.

| компонент | объём | доля |
|---|---:|---:|
| `MAX.RES` + `PATCHES.RES` + `.WRL` резидентно в памяти | 19,12 MiB | 25 % |
| спрайт-листы юнитов (92 юнита, 1530 кадров, RLE-серии) | 32,64 MiB | 43 % |
| terrain-атлас (`SNOW_1`: 337 тайлов + 12 544 id + палитра) | 1,34 MiB | 2 % |
| UI/меню/HUD-картинки, курсоры, портретные FLC, аудио-хуки (остаток) | 22,06 MiB | 29 % |
| **итого рабочий набор** | **75,17 MiB** | 100 % |

Спрайты стоят 32,64 MiB при площади кадров 3,9 Мпикс (14,89 MiB в RGBA): кадр
хранится RLE-сериями (`SpriteRow`/`SpriteRun`), а не полной плоскостью.

Библиотека UI-картинок целиком (все 801 `simple` + `big` записи, декодированы):
**65,47 MiB в RGBA** при 16,53 MiB индексированного heap — это верхняя граница
для HD-кэша интерфейса, а не набор одного экрана.

### 1.3 Стоимость кадра при S = 1, 2, 4 (текущий CPU-рендерер)

Одна и та же сцена (тайлы карты + 92 спрайта) отрисована в логический кадр
`640·S × 480·S` с `zoom = 64·S` — то есть ровно то, что будет делать
HD-режим, если оставить нынешний по-пиксельный путь:

| S | логический кадр | RGBA кадра | медиана | минимум | fps (мин.) | к 1:1 |
|---:|---|---:|---:|---:|---:|---:|
| 1 | 640×480 | 1,17 MiB | 5,49 мс | 5,46 мс | 183 | 1,0× |
| 2 | 1280×960 | 4,69 MiB | 21,41 мс | 21,22 мс | 47 | 3,9× |
| 4 | 2560×1920 | 18,75 MiB | 83,37 мс | 83,04 мс | 12 | 15,2× |

Медиана/минимум из 20 кадров; между прогонами ±3 % (в соседнем прогоне 5,6 / 22,0 /
85,1 мс), отношения к 1:1 стабильны.

Рост ~S²: рендерер пишет каждый пиксель каждого тайла и спрайта отдельно.
**Вывод для развилки 3:** при S=4 нынешний CPU-путь даёт 12 fps — это не
играбельно; S=2 (47 fps) — верхняя граница без GPU/атласной работы.

## 2. Ассеты и HD-объём

Объём HD: `пиксели × S² × 4 B` (RGBA8). «×1» — исходное разрешение 640×480.

| класс | записей | кадров | пикселей | ист. MiB | RGBA ×1 | RGBA ×2 | RGBA ×4 |
|---|---:|---:|---:|---:|---:|---:|---:|
| тайлы (`.WRL`, уникальные) | 2567 | 2567 | 10 514 432 | 27,99 | 40,11 | 160,44 | 641,75 |
| спрайты юнитов/зданий | 92 | 1530 | 3 903 699 | 2,44 | 14,89 | 59,57 | 238,26 |
| тени `S_*` (маски) | 78 | 1360 | 3 733 740 | 0,47 | 14,24 | 56,97 | 227,89 |
| хром окна (`FRAMEPIC`/`PANELTOP`/`PANELBTM`) | 3 | 3 | 389 280 | 0,28 | 1,48 | 5,94 | 23,76 |
| панели/кнопки/поля UI | 491 | 491 | 1 152 719 | 1,10 | 4,40 | 17,59 | 70,36 |
| фоны меню/диалогов (640×480) | 38 | 38 | 9 370 685 | 7,03 | 35,75 | 142,99 | 571,94 |
| картинки (планеты, логотипы) | 113 | 113 | 5 799 808 | 4,81 | 22,12 | 88,50 | 353,99 |
| иконки `I_*` | 70 | 81 | 345 514 | 0,27 | 1,32 | 5,27 | 21,09 |
| маркеры/курсоры/портреты | 185 | 194 | 471 447 | 0,45 | 1,80 | 7,19 | 28,77 |
| шрифты (GNW-растры, 3 × 255 глифов) | 3 | 768 | 58 995 | — | 0,23 | 0,90 | 3,60 |
| не-картинки (ссылки/данные) | 758 | — | 0 | 0,12 | — | — | — |
| **итого** | | | **35 740 319** | **44,97** | **136,34** | **545,35** | **2181,42** |

Уточнения по классам:

- **Тайлы.** «~337» из ТЗ — это банк одной карты (`SNOW_1` = 337 тайлов). Банки
  24 карт — 154…411 тайлов; уникальных пар **(палитра карты, пиксели тайла)** —
  **2567**: одинаковые индексы под разной палитрой дают разные текстуры.
  Один тайл — 64×64 = 16 КиБ в RGBA.
- **`S_*`** — не цветные текстуры, а 1-битные маски затемнения (3,73 Мпикс ≈ 456 КиБ
  маски); в HD их можно не увеличивать, а растягивать/генерировать. RGBA-колонка
  для них — верхняя оценка по bounding box.
- **`D_*`** (32 записи по 8/24 байта) — таблицы кадров башни/анимаций
  (`GetFrameInfo`), **не кадры** и не картинки: пиксельного объёма нет.
- **29 изображений 640×480** (фоны меню, `FRAMEPIC`, `FACBUILD`, `CARGOPIC`, …).
  Одно такое в RGBA: 1,17 MiB при ×1, **4,69 MiB при ×2, 18,75 MiB при ×4**.
  Держать все 29 одновременно в ×4 (543 MiB) нельзя — нужен стриминг/декод по экрану.

### 2.1 Что это значит для квоты

Полный набор всех ассетов (136 / 545 / 2181 MiB) в VRAM не влезает ни при каком S —
он и не нужен: одновременно живёт рабочий набор матча. Оценка по измеренным
классам (тайлы *одной* карты + все спрайты + хром + панели/HUD + шрифты):

| набор | S=1 | S=2 | S=4 |
|---|---:|---:|---:|
| тайлы одной карты (337 × 64×64) | 5,27 MiB | 21,1 MiB | 84,4 MiB |
| спрайты юнитов (все кадры) | 14,89 | 59,6 | 238,3 |
| хром окна | 1,48 | 5,9 | 23,8 |
| панели/кнопки/поля | 4,40 | 17,6 | 70,4 |
| шрифты | 0,23 | 0,9 | 3,6 |
| **рабочий набор матча** | **≈26 MiB** | **≈105 MiB** | **≈420 MiB** |

Вывод: **S=2 укладывается в разумную квоту (~0,1 ГиБ), S=4 — ~0,4 ГиБ** и
требует либо отбора «что грузить», либо GPU-пути.

### 2.2 Объём поставки (`.ktx2`)

По измеренным битрейтам (см. §3): ETC1S на этой графике — 0,33…5,29 бит/пиксель
(типично 1,5–2), UASTC — 8,0…9,4. Оценка полного HD-набора:

| S | пикселей | `.ktx2` ETC1S @2 bpp | `.ktx2` UASTC @8 bpp |
|---:|---:|---:|---:|
| 1 | 35,74 Мпикс | 8,5 MiB | 34,1 MiB |
| 2 | 142,96 Мпикс | **34,1 MiB** | 136,4 MiB |
| 4 | 571,85 Мпикс | **136,4 MiB** | 545,4 MiB |

## 3. Транскодер KTX2 → RGBA8

### 3.1 Что доступно на этой машине

| вариант | доступность | зависимости | сборка (clean, release) | `unsafe` |
|---|---|---|---:|---:|
| **(a) `basisu` 0.1** — pure-Rust порт транскодера Basis Universal, бит-в-бит с C++ | есть на crates.io, собирается | **1** (`ruzstd`), 12 МБ исходников | **9,0 с** | 7 |
| **(b) `ktx-rs` 4.4.4** — pure-Rust порт KTX-Software/libktx | есть на crates.io, собирается | **9** без Vulkan/OpenGL (13 с ними: +`ash`, `libloading`), 6,9 МБ | **31,4 с** | 139 |
| **(b′) C libktx / KTX-Software** | **нет** ни в системе, ни в vcpkg; нужна CMake+MSVC сборка нативной библиотеки и FFI | C/C++ библиотека + сборка на каждой платформе | эталон собран: **10 с** (`cl /O2`, без zstd) | — |

Существенно: `ktx-rs` — уже **не C-обёртка**, а порт KTX-Software на Rust
(объявление «Rust port of Khronos KTX-Software»); C-обёртка — это устаревший
`libktx-rs` 0.3.3 (2021). Настоящий C-эталон — `basisu_transcoder` из upstream
Basis Universal (он же встроен в libktx). Он собран здесь MSVC 14.51 (`/O2`,
`/DBASISD_SUPPORT_KTX2_ZSTD=0`) и использован как **третий декодер** для
проверки байт-в-байт и для сравнения скорости.

### 3.2 Метод

Тестовые картинки — из реальной графики: тайл 64×64, его ×4 вариант 256×256,
`FRAMEPIC` 640×480 (окно), кадр `TANK` 44×45. Кодирование — in-process энкодером
`ktx-rs` в **ETC1S** (BasisLZ) и **UASTC LDR 4×4**. Каждая итерация — весь путь
загрузки (разбор контейнера + транскод), как его вызывает загрузчик ассетов;
`--iterations 30`, в таблице медиана. Выход хешируется FNV-1a 64.

### 3.3 Результат (медиана, мс на файл)

| файл | кодек | `.ktx2` | бит/пикс | encode, мс | **basisu (Rust)** | **ktx-rs** | **C-эталон** | FNV совпал |
|---|---|---:|---:|---:|---:|---:|---:|---|
| тайл 64×64 | ETC1S | 1,1 КиБ | 2,29 | 4,1 | 0,03 | 0,03 | 0,035 | да |
| тайл 64×64 | UASTC | 4,2 КиБ | 8,41 | 35,3 | 0,05 | 0,04 | 0,036 | да |
| тайл ×4 256×256 | ETC1S | 2,6 КиБ | 0,33 | 17,1 | 0,31 | 0,44 | 0,192 | да |
| тайл ×4 256×256 | UASTC | 64,2 КиБ | 8,03 | 2,0 | 0,33 | 0,39 | 0,117 | да |
| `FRAMEPIC` 640×480 | ETC1S | 33,5 КиБ | 0,89 | 106,8 | 1,41 | 1,74 | 1,239 | да |
| `FRAMEPIC` 640×480 | UASTC | 300,2 КиБ | 8,01 | 903,1 | 3,53 | 2,96 | 1,941 | да |
| `TANK` 44×45 | ETC1S | 1,3 КиБ | 5,29 | 4,1 | 0,03 | 0,04 | 0,037 | да |
| `TANK` 44×45 | UASTC | 2,3 КиБ | 9,37 | 9,7 | 0,03 | 0,02 | 0,018 | да |

Разброс между прогонами на этой машине — ±10–15 % (например, сумма ETC1S у
`basisu` в соседнем прогоне 1,65 мс вместо 1,79), отношения между декодерами
устойчивы; в таблице — один документированный прогон.

Пропускная способность (сумма по четырём файлам = 378 812 пикс):

| декодер | ETC1S, мс | ETC1S, Мпикс/с | UASTC, мс | UASTC, Мпикс/с |
|---|---:|---:|---:|---:|
| `basisu` (pure Rust) | 1,79 | **212** | 3,94 | 96 |
| `ktx-rs` (порт libktx) | 2,26 | 168 | 3,41 | 111 |
| C-эталон (`basisu_transcoder`) | 1,50 | **252** | 2,11 | 179 |

**Все три декодера дают побайтово одинаковый RGBA8** на всех 8 файлах
(FNV-1a 64 совпал: `959e7da5fdd4b62d`, `981a030dbd13bfb7`, `5cf08787d1b69745`,
`7b7d46aefb73e765`, `60c0c5743ada499d`, `56848f0c1ce8cb17`, `b7dde56f12a2083e`,
`a6559997a04c20d7`). Значит «быстрее» не покупается ценой других пикселей —
при переезде на другой декодер golden-хеши декода не меняются.

Колонка «encode» — скорость энкодера `ktx-rs` (порт KTX-Software), которым
собраны тестовые файлы; для R2 планируется `basisu` CLI (C++), это отдельный
build-time инструмент, а не рантайм.

### 3.4 Рекомендация

**Рантайм-транскодер — `basisu` 0.1 (pure Rust), пинится `=0.1.0`.**

Обоснование в цифрах:

1. **Точность.** Бит-в-байт с C-эталоном на нашем корпусе (8 файлов, три декодера) —
   требование «HD только презентация» выполняется: декод не вносит дрейфа.
2. **Скорость.** 212 Мпикс/с (ETC1S) и 96 Мпикс/с (UASTC — основной путь здесь
   медленнее, C-эталон даёт 179). Весь HD-набор целиком: **×2 — 0,68 с** (ETC1S)
   или 1,49 с (UASTC); **×4 — 2,70 с** или 5,95 с. Это разовая загрузка, а не
   кадровое время: одна 640×480-текстура — 1,4 мс (ETC1S), 3,5 мс (UASTC).
3. **Зависимость.** 1 транзитивный крейт (`ruzstd`), 9,0 с чистой сборки, 7 `unsafe`,
   никакого C/C++/CMake и нативной библиотеки в поставке. У `ktx-rs` — 9 крейтов,
   31,4 с, 139 `unsafe`; у C-варианта — нативная сборка на каждую платформу и FFI.
4. **Цена C-варианта.** C-эталон быстрее в 1,2× (ETC1S) и 1,9× (UASTC) по агрегату,
   на отдельных файлах до 2,8×; в абсолютных числах — до 1,6 мс на текстуру и
   0,1–3,7 с на весь набор при загрузке. Это не окупает нативную сборку, нативную
   библиотеку в поставке и FFI-границу.

Ограничения и что делать:

- Обе Rust-реализации молодые (`basisu` 0.1.0 — 2026-07, `ktx-rs` 4.4.4 — 2026-11).
  Митигация: пин точной версии **и** декод-хеши в golden (R2): хеш FNV/SHA
  декодированного RGBA по репрезентативному набору — расхождение = блокер.
- Если по качеству понадобится UASTC, декод замедляется в ~2,2× (96 Мпикс/с),
  а объём поставки растёт с 34 до 136 MiB при ×2 — решение по качеству, не по
  скорости.
- **Энкодер** остаётся build-time C++ (`basisu` CLI, R2): рантайм-крейт декодирует
  только, энкодера в нём нет. Это согласуется с планом (одна CI-машина, pin, hash).

Для развилки 2 («SDL3 Canvas + транскод KTX2→RGBA8 сейчас»): измеренный декод
подтверждает путь — полная загрузка HD-набора занимает от 0,68 с (×2, ETC1S) до
~6 с (×4, UASTC, худший случай), это время загрузки, а не кадра; BC7/ASTC на GPU
по-прежнему не нужны.

## 5. Что R0 фиксирует для плана

1. **Развилка 3 (кратность):** по умолчанию **S=2** — 47 fps в текущем
   CPU-рендерере и ~105 MiB рабочего набора; **S=4** — 12 fps и ~420 MiB, то есть
   только после GPU-пути (или с явной квотой и отбором ассетов).
2. **Развилка 2 (бэкенд):** подтверждена — транскод KTX2→RGBA8 на CPU стоит
   0,7–1,5 с на весь набор при ×2 (разовая загрузка), GPU-форматы не нужны.
3. **Транскодер:** `basisu` pure-Rust, C-эталон — только oracle для golden-хешей
   декода.
4. **Кэш/стриминг:** 29 полноэкранных 640×480-картинок в ×4 — 543 MiB; интерфейс
   грузится по экрану, а не целиком (иначе квота не сходится).
5. **Риск производительности:** текущий рендерер масштабируется ~S²; HD-режим
   требует атласов/GPU-пути независимо от выбора транскодера.
