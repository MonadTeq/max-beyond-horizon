# Руководство агента-программиста

Правила и порядок работы над кодом проекта **M.A.X. : Beyond Rust Horizon**
(BRH). Обязательно к соблюдению при любых изменениях кода.

## 1. Проект и структура

Полное название — **M.A.X. : Beyond Rust Horizon** (сокращённо **BRH**,
префикс `max-brh`). Ремейк на базе двух неизменяемых референсов — оригинальной
игры M.A.X. и порта M.A.X. Port.

| Каталог | Назначение |
|---|---|
| `max-brh/` | игровой клиент (Rust-workspace: `max_core`/`max_net`/`max_assets`/`max_render`/`max_app`) |
| `max-brh-server/` | выделенный игровой сервер (отдельный проект) |
| `max-brh-docs/` | документация (architecture, analysis, development, qa, glossary, style-guide) |
| `max-brh-qa/` | тестовый сьют; `max-brh-qa-tools/` — утилиты QA |
| `max-brh-cicd/` | CI/CD: `ci.sh` + `scripts/` |
| `max-brh-assets/` | референс/ремастер (выгрузка ресурсов) |
| `max-cpp-port/`, `max-original/`, `max-original-dasm/` | референсы (не изменяются) |

Термины — [`glossary.md`](../glossary.md); стиль — [`style-guide.md`](../style-guide.md).

## 2. Референсы-оракулы

- **`max-cpp-port/`** — канонический C++-код M.A.X. Port (git-субмодуль);
- **`max-original/`** — оригинальные данные игры;
- **`max-original-dasm/`** — артефакты обратной разработки.

Эти каталоги **не изменяются** ни при каких условиях. Они используются только
для сверки: прежде чем что-то реализовать, изучить, как это сделано в C++-коде;
не домысливать поведение.

## 3. Принципы разработки

1. **Оракул — первый источник истины.** Реализация сверяется с
   `max-cpp-port` построчно; в документации фиксируются ссылки на функции/строки.
2. **Детерминизм.** Симуляция (`max_core`) бит-в-бит совпадает с C++ (RNG,
   снапшот, CRC). Изменения, влияющие на состояние, отражаются в снапшоте/CRC
   и сверяются с C++-векторами (`max-brh/tools/*_vectors`).
3. **Визуальный паритет 1:1.** Каждый экран — по ресурсам и раскладке C++-порта.
4. **Не ломать контракт механик.** Игровые правила зафиксированы в
   [`game-mechanics.md`](../architecture/client/game-mechanics.md); перед правкой
   экономики/производства/боя — сверка с этим документом.

## 4. Валидация изменений

**Правило тулчейна (Windows-хост).** Рабочая машина — Windows с нативным
`rustup`/MSVC. Девелоперские проверки выполняются **нативно** (MSVC), без Docker:

```powershell
# Быстрая проверка логики (headless, без SDL3):
cargo check --no-default-features
cargo test --no-default-features
```

**Docker используется только** для полного CI-гейта (`ci.sh`, Linux + SDL/X11-
зависимости) и Linux-сборок (`release.sh`), а также когда нужна эталонная
«зелёная» сверка default-фич (SDL3 из исходников). Быстрые dev-прогоны в Docker
гонять не требуется.

Полный гейт, который делает изменение «готовым»:

```sh
bash ci.sh   # cargo check/test (default/sound/headless), Horizon, QA, golden, soak
```

Обязательные проверки:

- `cargo check`/`cargo test` в трёх конфигурациях (default, `--features sound`,
  `--no-default-features`) — финально через `ci.sh`;
- QA-сценарии `max-brh-qa/scripts/*.qa` (падение любого assert — ошибка);
- golden-сверка (`qa_golden_check`) — дрейф 0 (порог 1 %);
- soak (100/120 ходов);
- сборка Windows: игровая (`build-windows-ui.ps1`) и консольная
  (`build-windows-console.ps1`) — нативный MSVC.

Golden-кадры переснимаются только осознанно, с объяснением в коммите.

## 5. Работа с git

- Коммит — после каждого завершённого этапа; сообщение описывает суть и
  подтверждающие тесты.
- **Не трогать оракулы** (`max-cpp-port/`, `max-original/`, `max-original-dasm/`).
- Побочные файлы тестов (`max-original/save10.*`) восстанавливать
  (`git checkout`) перед коммитом.
- Один коммит — одна логическая задача; документация и код — вместе.

## 6. Процесс QA и закрытие целей

- **Цели не закрываются без явного подтверждения человека.** Статус «выполнено»
  ставится только после того, как человек подтвердил, что найденные ошибки
  исправлены и цель можно закрыть. Автоматические прогоны — необходимое, но не
  достаточное условие (см. [`qa/README.md`](../qa/README.md)).
- Ошибки из ручного тестирования фиксируются и остаются открытыми до
  подтверждения.

## 7. Документация

После каждого изменения обновлять:

- [`CHANGELOG.md`](../../CHANGELOG.md) — запись в `[Unreleased]`;
- [`visual-1to1-status.md`](../analysis/visual-1to1-status.md) — при изменении
  визуала/механик;
- план/статус целей ([`architecture/client/README.md`](../architecture/client/README.md)) —
  только фактическое состояние, без преждевременного «выполнено».

Документация ведётся по [`style-guide.md`](../style-guide.md): профессиональный
стиль, терминология из [`glossary.md`](../glossary.md), без сленга и эмодзи.

## 8. Сборка и артефакты

- Артефакты — в `bin/` (`bin/release/` — основные сборки, `bin/target/` —
  промежуточная cargo-сборка); каталог легко удалить целиком.
- Windows-сборки — нативный MSVC (без Docker/mingw); Docker — только для
  Linux-сборок и CI-гейта.
- Термины сборки — [`glossary.md`](../glossary.md) §3.
