# UI-лобби выделенного сервера

Отдельный контур интерфейса, который обслуживает **выделенный сервер**
(`max-brh-server`, протокол Horizon). Это **не игра** и не часть игрового
клиента `max-brh`: лобби управляет сессиями (список/создание/вход/админ),
а сама игра идёт в игровом клиенте через ENet-сессию. Путать эти два слоя
нельзя — у них разные циклы жизни, разный транспорт и разные пользователи.

## 1. Границы

```
UI-лобби (отдельная поверхность)          Игра (max-brh + max-brh-server-арбитр)
───────────────────────────────────       ───────────────────────────────────
- список игр, создать/войти/выйти         - lockstep-симуляция, кадр, ввод
- админ: статус/стоп/рестарт/старт        - тикеты сессий, релей пакетов
- работает до входа в партию               - работает внутри партии
- транспорт: gRPC horizon.v1 (WS-паритет) - транспорт: ENet/UDP + gRPC-тикет
```

Лобби **не знает** игрового состояния и не меняет его; оно лишь оркестрирует
жизненный цикл сессии. Всё, что касается хода партии, принадлежит игре.

## 2. Два контура лобби

### 2.1 Игровой лобби (игрок)

Для игрока, который ищет/создаёт партию:

- `ListGames` — список открытых партий (заголовок, карта, команды, слоты);
- `CreateGame` — создать партию с настройками (world, teams, режим, таймеры);
- `JoinGame` — войти в слот; сервер возвращает **тикет** (ENet host/port +
  сессионный ключ), с которым игровой клиент поднимает UDP-сессию.

После `JoinGame` лобби передаёт управление игровому клиенту; само лобби до
конца партии больше не участвует.

### 2.2 Админ-консоль (оператор)

Для владельца/администратора сервера:

- `AdminListSessions` / `AdminSessionStatus` — что сейчас крутится и его состояние;
- `AdminSessionStart` / `AdminSessionRestart` — поднять/перезапустить сессию;
- `AdminSessionStop` — снять сессию.

Админ-консоль — это отдельная поверхность от игрового лобби (другой набор
методов, другой допуск через `admin`-секрет). Её нельзя мешать ни с лобби
игрока, ни с игрой.

## 3. API

RPC-схема — `max-brh-server/proto/horizon.proto`, сервис `horizon.v1.Horizon`:

| Метод | Контур | Назначение |
|---|---|---|
| `Hello` | общий | handshake, возможности сервера |
| `ListGames` | игровой | список открытых партий |
| `CreateGame` | игровой | создать партию |
| `JoinGame` | игровой | войти в слот → тикет ENet |
| `AdminListSessions` | админ | список живых сессий |
| `AdminSessionStatus` | админ | состояние одной сессии |
| `AdminSessionStop` | админ | остановить сессию |
| `AdminSessionRestart` | админ | перезапустить сессию |
| `AdminSessionStart` | админ | запустить сессию |
| `Ping` | общий | keep-alive |

gRPC-контракт дублирует WebSocket-JSON-протокол Horizon (одна RPC на пару
запрос/ответ, ключи JSON повторяют поля proto). Подробности — в
[protocol-grpc.md](protocol-grpc.md) и [protocol.md](protocol.md).

## 4. Поток «лобби → игра»

1. Игрок открывает **лобби**, получает список партий (`ListGames`).
2. Выбирает слот / создаёт партию (`CreateGame`, затем `JoinGame`).
3. `JoinGame` отдаёт **тикет**: `host:port` ENet + сессионный ключ/токен.
4. Игровой клиент (`max-brh`) подключается по UDP (ENet) и входит в
   lockstep-сессию; барьеры и CRC — внутри игры (см.
   [barrier-flow.md](barrier-flow.md)).
5. По окончании партии клиент возвращается в лобби.

## 5. Текущее состояние и план

- **Реализовано (сервер):** весь RPC-контур лобби и админа в `max-brh-server`
  (gRPC + WS-паритет), тикеты и спавн C++-headless арбитра —
  [dedicated-server-plan.md](dedicated-server-plan.md).
- **Реализовано (клиент):** игровое меню **Multiplayer** в `max-brh`
  обращается к `ListGames`/`JoinGame` — это промежуточный «лобби-клиент»,
  встроенный в игру.
- **Цель (отдельная поверхность):** вынести UI-лобби в самостоятельный
  артефакт/клиент (игровой лобби + админ-консоль), не связанный с игровым
  окном, чтобы жизненный цикл «до партии / вне партии» не смешивался с
  игровым циклом.

Порядок: сначала зафиксировать контракт лобби (proto уже есть), затем админ-
консоль как отдельный UI, затем при необходимости отдельный игровой лобби.
