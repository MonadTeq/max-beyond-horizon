# max-unity-client — оценка и план Unity-клиента M.A.X.

Краткая выжимка из [REPORT.md](REPORT.md) (полная оценка, фазы, риски, таблицы переиспользования — там).

## Решение за 30 секунд

- **Архитектура: вариант B.** Unity — оболочка (визуал/UI/ввод/звук), Rust — симуляция и сеть
  (`max_core` + `max_net` через FFI, cdylib). Детерминизм и сеть остаются **бит-точными**,
  потому что это тот же код и те же 692 Rust-теста; Unity-слой не участвует в lockstep.
- **Трудоёмкость:** реалистично **≈ 89 человеко-дней ИИ-агента**
  (оптимистично 65 / пессимистично 115).
- **Календарь:** 1 агент ≈ **18 недель** (13–23); 2 агента параллельно ≈ **11 недель** (8–14).
- **Нового кода:** ≈ 11–15 тыс. строк (C# рендер/UI/ввод + FFI-клей), против 86 тыс. строк уже существующего Rust-клиента.

## Главные принципы

1. **Приёмка только по пикселям.** Каждый экран проверяется diff-ом с уже существующими
   `max-rust-qa/golden/*.png` (порог 1 % → 0 % к релизу), а не на глаз.
2. **Code-first Unity.** Никаких сцен/prefab в git — всё кодом и ScriptableObject,
   чтобы параллельные агенты не конфликтовали в YAML.
3. **Всё «умное» остаётся в Rust.** Unity получает готовый draw-list (Frame API) и события;
   правила игры, ИИ, сеть и барьеры живут в нативной библиотеке и не дублируются.
4. **Сервер не меняется.** Horizon + C++ headless — готовые; Unity-клиент вписывается в
   существующий контракт (gRPC + ENet + lockstep-барьеры).
5. **Запасной мост.** Диагностический режим blit-моста (Rust рендерит кадр, Unity показывает)
   — страховка для локализации расхождений рендера.

## Что переиспользуется напрямую

`max_core` + `max_net` (как есть, в cdylib), оркестрация `max_app`, все спеки
(`docs/architecture/*`, `docs/analysis/visual-1to1-status.md`), 1069 PNG + `manifest.csv`,
10 golden-кадров, QA-фабрика (`suite/` 166 TC, `.qa`-язык, `qa_golden_check`), C++-векторы
детерминизма, серверная часть целиком.

## Открытые вопросы перед стартом

в CI; нужен ли мобильный/WebGL горизонт (если да — переоценка P4).
