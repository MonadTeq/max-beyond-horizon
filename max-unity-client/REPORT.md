# Unity-клиент M.A.X.: оценка трудоёмкости и план разработки силами ИИ-агентов

> Дата оценки: 2026-11-15 · Ревизия: 1.0 · Статус: оценка для принятия решения о старте.
> Входные материалы — существующий репозиторий `max-port-debug` (Rust-клиент v1.0.0, серверная часть, QA-фабрика, извлечённые ассеты).
> Единица оценки — **человеко-день ИИ-агента** (определение и калибровка — §8).

Ключевые числа, на которых строится оценка:

- Визуал **уже доказан 1:1 в Rust**: план A–F закрыт (недостаёт только FLIC-анимации портрета — осознанно отложена и в Rust).

- Сеть (gRPC + ENet + lockstep-барьеры) **уже работает живьём**: live-smoke 2 клиента × 10 ходов без таймаутов.

## 2. Варианты архитектуры и выбор

### 2.1 Сравнение вариантов

| Критерий | **A. Полный порт логики на C#** | **B. Unity-оболочка + Rust FFI** (рекомендован) | **C. Сервер-авторитет (рефакторинг)** |
|---|---|---|---|
| **Суть** | Переписать `max_core` (~40 тыс. строк) и `max_net` (~7 тыс.) на C#; симуляция крутится в Unity | Unity делает визуал/UI/ввод/звук; `max_core`+`max_net`+оркестрация компилируются в cdylib и вызываются через C API | Переделать игру из lockstep в клиент-сервер со снапшотами: изменить протокол, C++ headless, Horizon |
| **Детерминизм / бит-точность** | Нужно **заново доказать** бит-в-бит с C++-оракулом для всей симуляции и ИИ (порядок ГПСЧ, CRC16, векторы) — это основная статья затрат | **Гарантирован конструкцией**: это тот же машинный код; 692 Rust-теста + C++-векторы остаются валидными регрессиями | Lockstep-семантика уничтожается; требуется новая модель доверия, снапшоты, интерполяция |
| **Объём нового кода** | ~45–50 тыс. строк C# + полная повторная верификация | ~10–14 тыс. строк (C# рендер/UI/ввод + FFI-клей ~2–3 тыс. Rust) | Протокол + сервер + клиент: сопоставимо с A и **плюс** серверная часть, которая «готова и не меняется» |
| **Риск регрессий в будущем** | Два расходящихся клона логики (Rust-эталон и C#); каждое правило M.A.X. правится дважды | Одна реализация логики; Unity-слой изолирован и заменяем | Смена парадигмы затрагивает всё, включая эксплуатацию headless |
| **Отладка агентами** | Удобно (управляемый код, дебаггер) | Средне: FFI-шов требует дисциплины (см. §6), но логика остаётся дебагабельной в Rust-тестах | Как в A |
| **Лицензионная чистота / портируемость** | Всё в экосистеме Unity/.NET | Нужна сборка cdylib под каждую платформу (Windows/Linux/macOS) — решаемая задача, ENet уже vendored | Не влияет |
| **Оценка трудоёмкости (аг-дни)** | 220–350 (переписать + переверифицировать) | **≈ 89 реалистично** | 250–400 + серверная часть |
| **Совместимость с «сервер готов»** | Да | Да | **Нет** — противоречит условию задачи |

### 2.2 Решение: вариант B

**Выбираем B.** Причины, в порядке значимости:

1. **Детерминизм — решённая задача, и её нельзя «открывать заново».** Lockstep-клиент обязан симулировать мир бит-в-бит с headless-сервером C++, иначе CRC-барьер 45 порождает десинки. В Rust это уже доказано машинно (C++-векторы, live-smoke 2×10 ходов). Вариант A вынуждает повторить доказательство для каждого портированного модуля; вариант B оставляет доказательство в силе, потому что байты кода те же.
2. **Максимальное переиспользование работающего.** Через FFI переносятся не только симуляция и сеть, но и оркестрация режимов (`max_app`-уровень: фазы старта, hot-seat-цикл, AI-тики, таймеры), которая уже покрыта тестами `local_sp`, `hot_seat`, `start_phases`, `net`. Unity получает на вход **события и view состояния**, а не обязанности режиссёра партии.
3. **Проверяемость агентами.** Приёмка визуала — pixel-diff с уже существующими golden-кадрами; приёмка логики — прогон существующих `.qa`-сценариев. Обе петли обратной связи уже отлажены в Rust-проекте и переносятся без изобретений.
4. **Вариант C отвергается по условию задачи** (серверная часть готова и не меняется) и по смыслу: lockstep — ядро сетевой модели M.A.X.

### 2.3 Подварианты B (как именно Unity рисует)

| Подвариант | Суть | Плюсы | Минусы | Вердикт |
|---|---|---|---|---|
| **B1. Нативный рендер в Unity** | Все спрайты/атласы/шрифты — ассеты Unity; C# строит кадр 640×480 из view-данных | Настоящий «Unity-клиент»: UI-компоненты, звук, масштабирование окна — штатными средствами | Требует аккуратного воспроизведения pixel-пути (point filter, Gamma, палитры) | **Основной план (P2/P3)** |
| **B2. Blit-мост** | `max_render` (headless) рендерит кадр 640×480 в RGBA-буфер; Unity только показывает текстуру + шлёт ввод | Паритет бесплатный, playable-клиент за дни; идеален как «козырной» fallback | Не раскрывает потенциал Unity; ввод всё равно дублируется | **Опциональный разгон старта** в P0/P4 (стратегия снижения риска, см. §4.3) |

**Рекомендация по исполнению:** целевая — B1; B2 используется как промежуточная веха «первый playable-кадр» и остаётся в проекте как диагностический режим (`--bridge`), в том числе для изоляции расхождений «логика против рендера» при разборе pixel-diff.

## 3. Целевая архитектура (вариант B1)

### 3.1 Слои

```
Unity Player (C#, IL2CPP или Mono)
┌───────────────────────────────────────────────────────┐
│ GameFlow (режимы SP/HS/NET, экраны)                    │
│ InputMapper (мышь/клавиатура → FFI InputEvent)         │
│ Renderer (sprite-атласы, тайлы, GNW-текст, HUD, 640×480)│
│ Audio (SPW→AudioClip, теги max_app::audio)             │
│ NativeBridge (DllImport, единственный шов с Rust)      │
└───────────────────────┬───────────────────────────────┘
                        │ C ABI (новый крейт max_ffi)
┌───────────────────────▼───────────────────────────────┐
│ max_ffi (cdylib: max_core + max_net + max_app-headless)│
│  · жизненный цикл партии/сессии, конфиг, тик, ввод     │
│  · сеть: gRPC Horizon + ENet, барьеры, ретраи (tokio)  │
│  · view: снапшот состояния + UI-проекция + render-list │
│  · catch_unwind, arena-аллокации, детерминизм          │
└───────────────────────────────────────────────────────┘
        (по сети, уже готово, не меняется)
Horizon (max-horizon-server)  ⇄  C++ headless (src/)
```

### 3.2 Два интерфейса FFI (ключевое проектное решение)

1. **Control API** (редкие вызовы, JSON): `create_game(config)` / `start_net_session(...)` / `send_order(...)` / `load_save(...)` / `poll_events()` → события (`SessionJoined`, `BarrierTimedOut`, `Victory`, сообщения чата…). JSON оправдан: частота низкая, отладка агентами простая, обе стороны уже умеют serde_json/System.Text.Json.
2. **Frame API** (60 Гц, компактный бинарный буфер): `tick(dt, input_events) → FrameView`. FrameView — не «всё состояние», а **draw-list**: видимые тайлы (id + палитра мира), спрайты (тег, кадр, x/y, палитра команды), текст (шрифт, строка, x/y, цвет), UI-элементы, курсор, миникарта-данные (FOV-маска). Рендер-семантика (что и где рисовать) уже реализована в `max_app::panels/max_render::layout` — FFI её сериализует, а не переизобретает; Unity остаётся чистым композитором. Буфер переиспользуется (arena) — ноль аллокаций на кадр со стороны Rust, парсинг в C# через `Span<byte>`.

### 3.3 Поток кадра и детерминизм

- Unity `Update()`: копит `dt` → `tick` (тик симуляции с фиксированным шагом, как сейчас); рендер — 60 Гц по последнему FrameView.
- Рендер-частота **не влияет** на симуляцию: сетевое кадровое пейсингование (`01` каждые ~2 мс) живёт внутри нативной стороны, как и сейчас.
- Никаких плавающих преобразований координат: весь матпинг «клетка↔пиксель» — целочисленный (и уже проверен).
- Палитры и индексы прозрачности передаются как есть; sRGB/линейное преобразование в Unity **отключено** (см. §6, риск R5).

### 3.4 Платформенная матрица

| Платформа | Rust-таргет | Статус |
|---|---|---|
| Windows x64 (Editor + Player) | `x86_64-pc-windows-msvc` (cdylib) | основной |
| Linux x64 | `x86_64-unknown-linux-gnu` (cdylib) | второй приоритет |
| macOS (Apple Silicon/Intel) | `aarch64-apple-darwin` / `x86_64-apple-darwin` | факультативно |
| iOS / Android / WebGL | — | **вне области** этой оценки (IL2CPP AOT + статические линковки — отдельный проект) |

## 4. Разбивка по фазам с трудоёмкостью

Оценки в **человеко-днях ИИ-агента**; формат: реалистичная (оптимистичная–пессимистичная). Калибровка единицы — §8.

### P0. Unity-проект, структура, пайплайн — 7 д (5–9)

**Задачи**
1. Выбор версии Unity (рекомендация: Unity 6 LTS), создание проекта **code-first**: никаких сцен/prefab в git, всё генерируется кодом + ScriptableObject (минимум merge-конфликтов `.meta`/YAML между агентами).
2. Структура asmdef: `Max.Unity.Core` (FFI), `Max.Unity.Render`, `Max.Unity.UI`, `Max.Unity.Flow`, `Max.Unity.Tests`.
3. Editor-автоматизация для агентов: `-batchmode -nographics -executeMethod`, сборка плейера из CLI, вход/выход в Play Mode без GUI.
4. **Лицензия и headless-активация** (см. риск R2): личный/организационный ключ, `.ulf`, GameCI-контейнер или self-hosted runner.
5. Тест-каркас: Unity Test Framework (PlayMode) + **capture-харнесс**: off-screen-камера → `RenderTexture` 640×480 → PNG; порт `qa_golden_check` (pixel-diff, порог 1 % на старте → 0 % к релизу).
6. Скелет NativeBridge: `DllImport` на тестовый cdylib (`max_ffi_version()`), раскладка нативных библиотек в `Assets/Plugins/x86_64`.
7. CI: сборка проекта + прогон одного smoke-теста + прогон Rust-сборки cdylib в одном workflow.

**Риски:** лицензия/активация в batchmode (главный); домен reload в Editor (включить Enter Play Mode без domain reload, нативная сторона — `OnceLock`); расхождение цветовых пространств на старте (сразу выставить Gamma).  
**Критерий готовности:** CI зелёный: пустая сцена → capture 640×480 → PNG совпадает с эталонным «пустым» кадром; FFI-вызов версии проходит из PlayMode-теста.

### P1. Импорт ассетов (PNG → спрайты/атласы, палитры, шрифты) — 10 д (7–13)

**Задачи**
1. Editor-импортер по `max-brh-assets/images/manifest.csv`: 1069 PNG → `Texture2D` с **Point-фильтром, без mipmaps, без sRGB, без сжатия**; UI-подмножество — в атласы по экранам (FRAMEPIC/панели/кнопки/курсоры), спрайты юнитов — мультикадровые листы с `frames`/`hotx/hoty` из manifest.
2. Палитры: `COLOR.PAL`, палитра `FRAMEPIC`, палитры команд (`COLOR_*`/тинтирование) как ассеты-таблицы; LUT-шейдер или предзапечённые per-team атласы — решить прототипом в P3.
3. GNW-шрифты (`FONT1/FONT2/FONT5`, 12 КБ, эталоны в `max_render/data/`) → glyph-атлас + метрики + рендер строк (обводка/тень — уже специфицированы); юнит-тест на «?»-центрирование (аналог `quest_caption_is_centered_like_cpp`).
4. `.WRL`: тайловый атлас мира (337 уникальных тайлов × палитра мира; 6-битная VGA-палитра → растяжение 8 бит) — конвейер «WRL → PNG-атлас» в Editor (или на Rust-стороне `max_assets` и передача байтов).
5. Звук: конвертер SPW (WAV PCM 22050/16/моно) → `AudioClip` (прямая загрузка WAV-байтов), таблица тегов `MAX.RES` → файлы (607 wav-ref).
6. Валидация импорта: тест-сверка нескольких декодированных картинок с `max-brh-assets/images/*.png` (byte-equal) — ловит ошибки фильтра/цветопространства на раннем этапе.

**Риски:** sRGB/компрессия «протекут» в дефолтах импортера (лечится пресетом `TextureImporter` + тестами); атласизация RLE-картинок с прозрачностью; мультикадровые курсоры (вертикальная укладка).  
**Критерий готовности:** все 1069 ассетов импортируются одной командой Editor; тесты byte-equal на выборке; GNW-строка «Game Over» совпадает с golden-кадром.

### P2. Экраны 1:1 (меню/настройка/фазы старта/панели/HUD) — 16 д (12–20)

**Задачи** (спеки: `visual-1to1-status.md` §2.4, §10–11; эталоны: `golden/*.png`)
1. Каркас экранов: логический канвас 640×480, стек/переходы, маппинг кликов, целочисленное масштабирование окна + letterbox + обратный пересчёт (как `frame_scale`).
2. Главное меню (`MAINPIC`, `MNUBTN*`, GNW-подписи), Create/Join (`PLANETSE`-грид планет, `MULTGAME`-список), Multiplayer Menu.
3. Настройка: Options (6 панелей, 71 item, 51 control), Planet (3×2 карты), Players (4 слота, флаги, эмблемы), Clan (8 карточек), Help-заглушки в объёме Rust.
4. Фазы старта: CargoMenu/мобилизация (`CARGOPIC`), выбор точки высадки (карта на зуме 4), окно hot-seat-перехода (`HELPFRAM` + OK).
5. HUD в игре: хром `FRAMEPIC`, `PANELTOP`/`PANELBTM`, портрет (статичный кадр, как в Rust), 4 строки статистики, сетка переключателей (SURVEY/STATUS/…), зум-слайдер, End Turn/счётчик хода/таймер, координаты/описание юнита, кнопки Files/Prefs/Help/Reports/Chat.
6. Диалоги/сообщения (`DialogMenu`, INFO/MODAL), экран победы/поражения (`ENDGAME1..9`, колонки статистики).
7. Pixel-diff-приёмка каждого экрана против golden (порог → 0 %, с масками на отложенное: FLIC-портрет, Help-экраны).

**Риски:** самый объёмный визуальный код; «почти совпадает» ≠ «совпадает» (приёмка только по diff-утилите, не на глаз); порядок слоёв/якоря (`blit_simple_anchored`-нюанс уже задокументирован — перенести тестом).  
**Критерий готовности:** `visual-screens.qa`-эквивалент в Unity даёт 10/10 golden-кадров с diff = 0 (кроме согласованных масок); UI-ввод (клики/Enter/Esc) проходит сценарий «меню → настройка → партия» на FFI-заглушке.

### P3. Игровое поле и ввод (тайлы/спрайты/зум/миникарта/курсоры) — 18 д (13–23)

**Задачи**
1. Рендер тайлов: атлас мира → кадр 448×448 (WINDOW_MAIN_MAP) на всех зумах (64→4 px/клетку, nearest-neighbour); dirty-rect или полный redraw (307 кп/кадр — посильно CPU-путём; GPU-вариант — оптимизация).
2. Спрайты юнитов/зданий с тенями `S_*`, командными цветами (LUT или per-team атласы), порядок отрисовки (GroundCover→MobileLandSea→Stationary→MobileAir — уже описан для CRC), маркеры ресурсов (`RAWMSK*`/`SMRWMK*`, кадр по `amount` и зуму), обломки.
3. Миникарта 112×112: FOV-маска из heat map, точки юнитов, рамка камеры, `2x`/`TNT` (поведение 1:1 из `Access_UpdateMinimapFogOfWar`).
4. Курсоры: 30 курсоров с анимацией и hotspot, контекстное переключение (как `max_app::cursor`).
5. Ввод: выделение (клик/рамка), приказы move/attack/build через клик и rclick, предпросмотр пути (`PTR_PATH`), скролл-полосы/edge-scroll, зум колесом/слайдером, hotkeys, блокировка ввода на ходу ИИ/окне перехода.
6. Прокрутка карты, координаты клетки, tooltip-описания юнитов.

**Риски:** палитровые тинтирования команд (главный визуальный риск — валидировать прототипом в начале фазы); производительность (профиль-тест с бюджетом 16 мс); зум 4 (112×112 на 448×448) и маркеры малых зумов.  
**Критерий готовности:** golden `game.png`/`hs-game.png` с diff = 0 на сцене с юнитами/маркерами/миникартой; сценарий ввода (выделить → приказ → End Turn) проходит с реальным `max_core` через FFI.

### P4. FFI-обвязка (core + net) и интеграция — 12 д (9–16)

**Задачи**
1. Новый крейт `max_ffi` в workspace `max-brh` (crate-type `cdylib`, без SDL): C ABI (ручной `#[no_mangle] extern "C"` или cbindgen), `panic=abort` off + `catch_unwind` на шве, код ошибки/логи в ring-buffer для Unity-лога.
2. Control API (JSON): конфиг партии, pregame-фазы, приказы (08/38/41/50…), End Turn/чат/пауза, save/load (MXLS, V70 read), сетевая сессия (лобби gRPC, ретраи `JoinRetryPolicy`, handshake-фолбэк хэшей — всё уже в `max_app::net`).
3. Frame API: сериализация FrameView (draw-list + UI-проекция) в arena-буфер; события наружу (колбэк-очередь, опрашиваемая из Unity).
4. tokio-рантайм на фоновом потоке внутри библиотеки; никаких блокирующих вызовов из Unity-потока; таймауты/ретраи на нативной стороне.
5. Интеграция: `GameFlow` связывает P2/P3-рендер с живой симуляцией — SP-партия «меню → настройка → фазы → ходы → победа» на реальном `max_core`.
6. Сборка cdylib в CI (Windows/Linux) + раскладка в `Assets/Plugins`; смоук «Unity → Rust: 5 ходов против ИИ» в batchmode.

**Риски:** владение памятью на шве (arena + «не освобождай чужое»); домен reload Editor (двойная инициализация рантайма); ABI-стабильность версий Rust; паника через FFI.  
**Критерий готовности:** локальная партия играбельна в Editor и в собранном Windows-плейере; `cargo test` workspace остаётся зелёным (FFI — аддитивный крейт); детерминизм: CRC из FFI == CRC Rust-клиента на том же сценарии (тест TC-10xx-паритета).

### P5. Режимы SP/HS/NET + звук — 12 д (9–16)

**Задачи**
1. M-SP: цикл ходов с ИИ (тики, `end_turn_retry_counter > 120`), таймер хода, пауза, экраны фаз — всё через FFI-оркестрацию; золотые сценарии `sp-full.qa`.
2. M-HS: окно перехода «Red Team: Begin turn.», заморозка таймера на окне, переключение `player_team`, блокировка чужого ввода, 2–4 игрока + ИИ вперемешку (`hs-2.qa`).
3. M-NET: экраны Create/Join (список игр, пароль, статусы «Session warming up — attempt N/M»), чат (18), пауза (39/40/46), десинк-статус (51), реконнект-статусы; live-smoke «2 Unity-клиента × 10 ходов» (batchmode `-nographics` достаточно: симуляция в Rust).
4. Звук: мэппинг событий (`max_app::audio`-теги: клики меню, юниты, выстрелы) → AudioClip; микшер громкости; тихий fallback.
5. Оконное поведение: масштабы 1×/2×/…, letterbox, ресайз, выход/сохранение партии (MXLS-диалоги).

**Риски:** сетевой дебаг через FFI (статусы/логи должны быть видимы в Unity-логе — ring-buffer из P4); тайминги hot-seat; два одновременных живых клиента в CI (порты, тикеты).  
**Критерий готовности:** все три режима проходят свои `.qa`-сценарии и golden; живой сетевой smoke 2×10 зелёный в CI.

### P6. QA-паритет и релизный пайплайн — 14 д (10–18)

**Задачи**
1. Порт `.qa`-драйвера в Unity: тот же язык сценариев (click/rclick/key/type/wait/tick/shot/assert/menu/…), исполнение в PlayMode-тестах с детерминированным степпингом; `--record`-аналог из живого плейера.
2. Golden-харнесс в CI: capture → PNG → сравнение с `max-brh-qa/golden/` (порог 0 % к релизу; в репозитории Unity — свои golden, сверенные с Rust-эталонами).
3. Перенос матрицы `suite/` (166 TC, 11 областей) как чек-листа приёмки: каждый TC — ссылка на Unity-автоматизацию/UNIT/SMOKE/MANUAL (как в Rust-проекте).
4. Паритет детерминизма: тест «тот же сценарий → тот же CRC в Rust-клиенте и Unity-клиенте» (FFI-метод CRC); регресс-прогон векторов.
5. Производительность: профиль-тесты (бюджет кадра, аллокации/кадр через FFI — ноль); стресс-тест долгой партии.
6. Релизный пайплайн: сборка плейеров Win/Linux, версионирование, changelog, зеркало `release-checklist.md`; оконные прогоны реального бинаря кликами user32 (паттерн `ui-test-*.ps1`).

**Риски:** недетерминизм кадра в Unity (порядок отрисовки, время) — степпинг тестов должен быть детерминирован; расхождения платформ (D3D/Vulkan) в pixel-diff — фиксировать API рендера в тестах.  
**Критерий готовности:** полный CI зелёный (Unity-тесты + golden + live-smoke 2×10 + сборки); матрица TC закрыта не хуже, чем в Rust-проекте; релизный чек-лист выполнен.

### 5.2 Календарь

| Сценарий | Аг-дней | Недель (1 агент) | Недель (2 агента) |
|---|---:|---:|---:|
| Оптимистичный | 65 | ≈ 13 | ≈ 8 |
| **Реалистичный** | **89** | **≈ 18** | **≈ 11** |
| Пессимистичный | 115 | ≈ 23 | ≈ 14 |

Календарь при 2 агентах построен по критическому пути:

```
P0 (7 д, 1 агент; хвост P0 параллелится с P1)
  ├─ Агент A: P1 (10) → P3 (18)                = 28 д
  └─ Агент B: P2 (16) → P4 (12)                = 28 д
Интеграционный шов (P4↔P2/P3)                 + 2 д
P5 (двое)                                      ≈ 7 д
P6 (двое, часть параллельна хвосту P5)         ≈ 8 д
────────────────────────────────────────────────────
Итого ≈ 7 + 28 + 2 + 7 + 8 = 52 раб. дня ≈ 10.5 недель (+10 % накладных ≈ 11)
```

### 5.3 Что можно параллелить

- **P2 ∥ P3** — разные подсистемы и экраны; общий код — только рендер-ядро, которое фиксируется в первые 2–3 дня P2 (контракт: draw-примитивы + canvas 640×480).
- **P4 ∥ P2/P3** — FFI-крейт живёт в `max-brh` и тестируется `cargo test` независимо от Unity; интеграция ждёт только скелетов P2/P3.
- **P1 ∥ хвост P0** — импортер пишется, как только создан проект и пресеты.
- **P6-подготовка ∥ P4** — порт `.qa`-драйвера и golden-харнесса можно начинать на FFI-заглушках.
- **Звук (часть P5) ∥ P3** — не зависит от игрового поля.

Не параллелится: P5 требует P4+P2+P3; P6 — всё предыдущее; P0 целиком — фундамент.

## 8. Допущения и калибровка оценок

**Определение единицы.** «1 человеко-день ИИ-агента» — полный рабочий день агента с готовым контекстом (спеки, оракулы, golden-эталоны, образцы кода), включая написание кода, прогон тестов и golden-сверку. Среда: Unity Editor через CLI/batchmode + Test Runner + скрипты; визуальная приёмка — пиксельное сравнение, а не «на глаз».

**Калибровка.** Оценки выведены из фактической скорости проекта: Rust-клиент (86 тыс. строк, 692 теста, три режима, QA-фабрика) построен агентами по тем же спекам; порт наследует все спеки и эталоны, поэтому скорости приняты на уровне «проверенного рефакторинга под новую оболочку», а не «новой разработки»: UI-экран со специфицированной раскладкой и golden-эталоном — 0,5–1,5 д; подсистема рендера (тайлы/спрайты/миникарта) — по 3–5 д на блок; FFI-крейт — по фактической сложности `max_net` (7 тыс. строк).

**Границы оценки (сознательно вне объёма, паритет с Rust-клиентом):** FLIC-анимация портрета; полная запись V70 (локальный сейв — MXLS); конкурентный `SimultaneousMoves`; экраны Help/Scenarios; iOS/Android/WebGL.

**Открытые вопросы для старта P0:** точная версия Unity и редакция лицензии; выбор IL2CPP/Mono для desktop-релиза; допустимый порог golden-диффа в CI (1 % на старте, 0 % к релизу — принять явно); нужен ли WebGL/мобильный горизонт (если да — переоценка P4 и общей суммы).

## 9. Порядок запуска (первые шаги)

1. **P0**: поднять проект + лицензию + batchmode-пайплайн + capture-харнесс; смоук FFI `max_ffi_version()`.
2. Параллельно: P1 (агент A) и P2 (агент B); затем P3 (A) и P4 (B).
3. Первая интеграционная веха: локальная SP-партия в Editor (конец P4).
4. P5 → P6 → релизный чек-лист (зеркало Rust-проекта).
