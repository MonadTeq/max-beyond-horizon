# План: Dedicated Server для M.A.X. на базе Horizon + изменения клиента

Версия: 0.1 (черновик для обсуждения) · 2026-11-12

Цель — поднять выделенный сервер (dedicated server) для M.A.X. Port, который
работает без участия игрока-хоста: круглосуточные публичные игры, серверные
ИИ-команды, лобби/матчмейкинг, администрирование. В `max-horizon-server/` лежит
готовый Rust-фреймворк игрового сервера (WebSocket/WebTransport, плагины,
событийная шина, GORC-репликация) — он станет управляющей плоскостью, а
симуляция игры останется в родном C++-движке.

---

## 1. Ключевая проблема: M.A.X. — детерминированный lockstep, а не client/server

Сегодня сеть M.A.X. устроена так (изучил `src/remote.cpp`,
`src/transport_udp_default.cpp`):

- **Каждый пир симулирует весь мир** (детерминированно). По сети идут только
  *приказы и события*, а не состояние.
- Синхронизация — **барьеры**: покадровая синхронизация каждые ~2 мс
  (`Remote_Synchronize`, пакет 1), барьеры начала/конца хода (пакеты 00/52),
  CRC-барьер (45), аудит юнитов (23/24), owner-authoritative синк состояния
  (54 — добавлен в нашем форке, коммиты `b2d0700`, `5ff247d`).
- «Сервер» сейчас — это просто игрок-хост (первый пир, ENet server role,
  `Remote_Lobby(true)`); он же играет за красных.
- Транспорт: ENet/UDP, пакеты ≤ 1440 байт, хендшейк версий
  (`TRANSPORT_PACKET_00`), mesh-соединения после обмена списком пиров.

Следствия для dedicated server:

1. «Честный» server-authoritative (сервер хранит состояние, клиенты — тонкие)
   = переписать сетевую модель игры. Нереально в разумный срок.
2. Прагматичный путь: **сервер = headless-пир**, который ведёт ту же
   детерминированную симуляцию и работает арбитром/хостом. Все механизмы уже
   есть; нужен headless-режим и переключение «хозяина истины» с игрока на
   сервер.
3. Horizon при этом закрывает то, чего в игре нет вообще: лобби, сессии,
   авторизация, метрики, администрирование, ретрансляцию.

## 2. Варианты архитектуры

| # | Вариант | Что делаем | Оценка | Вердикт |
|---|---|---|---|---|
| A | **Headless-пир + Horizon-управление** | max-port в режиме без видео/аудио/UI — игровой хост и арбитр; Horizon — лобби/сессии/админ | ~2-3 мес до MVP | **рекомендуется** |

## 3. Целевая архитектура

```text
                        Horizon Server (Rust, max-horizon-server/)
  ┌──────────────────────────────────────────────────────────────────┐
  │  WS/WebTransport listeners (config.toml)                          │
  │   ├─ max_lobby    — список игр, создание/вход, матчмейкинг        │
  │   ├─ max_auth     — выдача сессионных тикетов (uuid + подпись)     │
  │   ├─ max_session  — Process Manager: спавн/health/restart headless │
  │   │                 max-port, выделение UDP-портов, маппинг сессий │
  │   ├─ max_chat_bridge — WS-чат ↔ игровой чат (REMOTE_PACKET_18)     │
  │   ├─ max_metrics  — игроки/ходы/десинки в мониторинг               │
  │   └─ max_admin    — kick/ban/pause/save/restart команды            │
  │   GORC: метаданные сессий как объекты (позиции игроков для лобби)  │
  └───────────────┬──────────────────────────────────────────────────┘
                  │ spawn/stop, конфиг (CLI/JSON), тикеты
        ┌─────────▼──────────┐
        │  max-port.exe      │  headless-сборка (MAX_HEADLESS)
        │  роль: TRANSPORT_SERVER (хост-пир)                          │
        │  - полная симуляция (своя копия мира)                        │
        │  - арбитр: валидация приказов, сервер-авторитет при          │
        │    рассинхроне (инверсия owner-authoritative из форка)       │
        │  - ИИ-команды (TEAM_TYPE_COMPUTER)                           │
        │  - автосейвы сессии (слот 10 — рестарт при десинке)          │
        │  - сбор отчётов (desync-turn*.txt) от пиров                 │
        └─────────▲──────────┘
                  │ ENet/UDP :31554 (или выделенный порт сессии)
      ┌───────────┴───────────┐
      │ Client (max-port.exe) │  обычная игра, изменения ниже
      │  - WS: список серверов, тикет
      │  - ENet: игровой трафик как сегодня
      └───────────────────────┘
```

Фазы 0-1 не требуют менять сетевую модель; фаза 2 делает сервер арбитром.

## 4. Что делаем в Horizon (серверная сторона)

Horizon даёт почти всё из коробки: listeners (WS `json`/`bitcode`, сжатие
zstd/lz4; опционально WebTransport/QUIC с датаграммами — пригодится для
ретрансляции в фазе 3), событийная шина (`core:*`, `client:*`, `plugin:*`,
`gorc:*`), плагины-динамические библиотеки, rate limiting, мониторинг, Docker.

Новые артефакты:

1. **Крейт `max_session` (Process Manager)** — единственная вещь, которой в
   Horizon нет: управление дочерними процессами.
   - API: `start_session(config) -> SessionHandle {port, pid, status}`,
     `stop_session`, `health_check` (heartbeat/выходной код), перезапуск при
     падении, лимиты ресурсов.
   - Каждая сессия = один headless max-port на своём UDP-порту
     (стратегия выделения портов из пула).
   - Конфиг сессии передаётся через CLI/JSON-файл: карта, режим, таймеры,
     команды/ИИ, автосейв-слот, пароль, лимит игроков.

2. **Плагин `max_lobby`** (события `client:max:list_games`, `create_game`,
   `join_game`): реестр сессий (название, карта, игроки, статус), проверка
   пароля, лимиты. GORC: сессия как объект с каналами metadata/status для
   живого обновления списка.

3. **Плагин `max_auth`**: тикет = `{session_id, player_id, exp, sig}` (общий
   секрет с headless-процессом). Клиент получает тикет по WS, предъявляет его
   в ENet-хендшейке (расширение `TRANSPORT_PACKET_00`). Без тикета сервер
   рвёт соединение — закрывает сегодняшнюю дыру «заходит кто угодно на порт».

4. **Плагин `max_admin`**: команды (kick/ban/pause/save/chat/restart) через WS
   админ-сокет → в headless-процесс по stdin/локальному каналу.

5. **`max_metrics` / `max_chat_bridge`** — как выше на схеме.

6. `config.toml`: секция `[max]` (путь к headless-бинари, пул портов,
   секрет тикетов, пути к данным игры и сейвам).

## 5. Изменения на клиентской стороне (по файлам)

### 5.1 Headless-режим (фаза 0, критический путь)

Новая опция сборки **`MAX_HEADLESS`** (CMake) + рантайм-флаг `--server`:

| Файл | Что меняется |
|---|---|
| `src/main.cpp` | диспетчер режимов; в server-режиме без меню: init ресурсов → программный сетап → `Remote_Lobby(host)` → `GameManager_GameLoop` |
| `src/svga.cpp` | SDL video driver `"dummy"` (окно не создаётся), отключить `SDL_StartTextInput`, мышь |
| `src/window_manager.cpp`, `gfx.cpp`, `drawmap.cpp`, `flicsmgr.cpp`, `movie.cpp` | заглушки отрисовки (пустые функции) под `#if defined(MAX_HEADLESS)` |
| `src/sound_manager.cpp` | no-op аудио (miniaudio не инициализировать) |
| `src/mouse.c`, `cursor.cpp`, `mouseevent.cpp` | без ввода |
| `src/menu.cpp`, `src/gamesetup.cpp`, `src/networkmenu.cpp` | выделить не-UI логику сетапа (она уже вызывается меню-функциями): собрать игру из конфига — мир, команды, кланы, таймеры — и запустить. Наш тест-драйвер (`build/hostclient-test.ps1`) уже доказал, что весь флоу проходит без единого действия в UI |
| `src/crash_reporter.cpp` | в server-режиме: лог в stdout/файл, отчёты в сессионный каталог |

Важно: headless-пир **не занимает команду** (сегодня хост авто-берёт красных
в `NetworkMenu::NetSync(0)`). В server-режиме хост = наблюдатель-арбитр;
старт игры — по команде Horizon (все игроки ready) или таймеру.

### 5.2 Транспорт (`src/transport_udp_default.cpp`)

1. **Тикет в хендшейке**: расширить `TRANSPORT_PACKET_00` (или новый пакет 04):
   `{game_version, enet_version, protocol_version, session_ticket}`;
   сервер проверяет подпись/срок, клиент — ожидаемый `session_id`.
   Несоответствие → `TRANSPORT_PACKET_03` (reject) с причиной.
2. **WAN-тайминги**: вынести `REMOTE_RESPONSE_TIMEOUT` (30 с), периоды пингов,
   размер очередей в конфиг; для серверной игры таймаут-политика — «пауза и
   ожидание», а не дроп (см. 5.3.4).
3. **Reconnect/Resume (фаза 2)**: при переподключении по тому же тикету сервер
   шлёт полный снапшот состояния (на базе пакета 54, который уже сериализует
   юнитов, золото, исследования, счётчики) и возвращает игрока в барьеры.

### 5.3 Игровой протокол (`src/remote.cpp`, `remote.hpp`)

1. **Сервер-авторитет (фаза 2)** — главное изменение логики. Сегодня истина —
   *владелец* юнита: `Remote_ApplyUnitState` берёт состояние от owner, а
   `Remote_ReceiveNetPacket_54` принимает пакет только от owner. Для DS
   владельцем истины становится сервер: коррекции применяются от сервера к
   любому пиру; пакет 54 от сервера — приоритетен; валидация приказов (23/38/41)
   против серверной симуляции (отклонять невозможные действия).
   Это ровно тот механизм, что добавил форк — меняем только направление.
2. **Новые REMOTE-пакеты (55+)**: `auth_result`, `server_chat` (системные
   сообщения), `desync_report_upload` (пир шлёт серверу содержимое
   `desync-turnN.txt` — сервер агрегирует и передаёт в Horizon), `pause_state`,
   `rejoin_snapshot`.
3. **Spectator (фаза 2)**: новый `TEAM_TYPE_SPECTATOR`/флаг — получает синк
   состояния (54) без команды, `all_visible` для него принудительно, не
   участвует в барьерах хода. UI-сторона — экран наблюдателя.
4. **Политика отключений**: опция `pause_on_disconnect` — при потере пира
   барьеры держатся с длинным таймаутом (индикатор «ждём игрока»), сервер
   может передать команду ИИ или кикнуть по команде админа.
5. **Детерминизм/данные**: в хендшейк добавить хеш данных
   (`MAX.RES`/`PATCHES.RES` SHA256 + версия); несовпадение — отказ с понятным
   сообщением. (Уже есть `ResourceManager_Sha256` для миров.)

### 5.4 Лобби/UI (фаза 1)

- Новый транспорт `"horizon"` (настройка `transport`): клиент коннектится к
  Horizon по WS (`libcurl`/минимальный WS-клиент или встроенный в
  `max-horizon-server` формат JSON), получает список игр и тикет, затем обычный
  ENet-коннект к адресу сессии.
- В `src/networkmenu.cpp`: вместо «Searching for hosts» — список серверов из
  Horizon (название, карта, игроки, пинг), кнопка «подключиться», ввод пароля.
- Настройки в `assets/settings.json`: `horizon_address`, `player_token` (позже
  — аккаунт), `spectator`.

### 5.5 Сборка

- `CMakeLists.txt`: опция `MAX_HEADLESS` (без GUI-зависимостей не выйдет
  полностью — SDL нужен, но без video/audio; miniaudio/SDL_mixer-инициализация
  отключаются), цель `max-port-server`.
- Фаза 1: зависимость WS-клиента (или написать тонкий WS поверх SDL-сокетов,
  чтобы не тащить boost).
- CI (`.github/workflows/build.yml`): job сборки headless-бинари.

рестарт при десинке работает с серверного сейва.

## 7. Риски и открытые вопросы

1. **Lockstep на WAN (главный риск).** Покадровый барьер раз в ~2 мс
   (`Remote_Synchronize`) на RTT 50–100 мс замедлит/застопорит симуляцию.
   Нужен эксперимент фазы 0: измерить деградацию с искусственной задержкой
   (наш pair-тест уже умеет всё воспроизводить); митигации: (а) адаптивный
   интервал кадрового барьера по RTT, (б) переход к синхронизации только по
   приказам с таймстампами (большое изменение `remote.cpp`), (в) input-delay
   в стиле файтингов. Без решения этого пункта DS будет «для близких
   регионов».
2. **Детерминизм**: все пиры должны иметь одинаковую сборку и данные —
   закрывается хешем в хендшейке (5.3.5), но разнородные платформы
   (Windows/Linux) надо прогнать pair-тестом — наш драйвер это позволяет.
3. **Десинк-рестарт**: сейчас каждый пир грузит автосейв из *своего* pref-каталога
   (`da11387`); на сервере истина — сейв должен раздаваться сервером
   (пакет 16 уже умеет передавать файл).
4. **Безопасность**: сегодня пир доверяет владельцу юнита (чит = правка
   клиента). Фаза 2 закрывает сервер-валидацией; до неё сервер пригоден
   только для доверенной аудитории.
5. **Лицензия/данные**: сервер так же требует оригинальные данные (MAX.RES) —
   распространять их нельзя; развёртывание — у владельца данных. Клиент
   остаётся MIT.
6. **Процесс-менеджер**: Horizon его не имеет; делать аккуратно (зомби-процессы
   на Linux, graceful shutdown, лимиты). Возможно, начать с systemd/контейнера
   на сессию и только потом встроить.

## 9. Прогресс (обновляется по мере реализации)

- **Фаза 0 — выполнена**: MAX_HEADLESS-сборка, headless-сервер-арбитр без
  своей команды, автостарт лобби, пассивные барьеры, ожидание сайт-селекта,
  CRC-сравнение, авторестарт при десинке; полный pair-тест пройден
  (2 клиента, 3–4 хода, 0 десинков). Детали: `build/server-phase0-status.md`.
- **Хендшейк v4 — выполнена**: тикет сессии (`session_ticket` /
  `server_session_ticket`) + SHA256-хеш данных в `TRANSPORT_PACKET_00`,
  reject `TRANSPORT_PACKET_03` с причиной (version/ticket/data); негативный
  тест с неверным тикетом пройден.
- **Крейт `max_session` (max-horizon-server/crates/max_session) — готов**:
  `SessionManager` (start/stop/restart/health/list/shutdown_all), пул портов,
  изолированная директория сессии (копия шаблона + `settings.json` с портом,
  тикетом и правилами игры), watchdog с рестартом при падении и backoff,
  генерация тикета для защищённых сессий. Сборка и 19 тестов проходят
  (`cargo test -p max_session`); интеграционный smoke-тест гоняет реальный
  headless-процесс при установленном `MAX_SESSION_TEST_EXE`.
- **Плагин `max_lobby` (max-horizon-server/crates/max_lobby) — готов**:
  клиентские события `max_lobby:list_games` / `create_game` / `join_game`,
  ленивый SessionManager из `MAX_*`-переменных, реестр сессий без хранения
  паролей/тикетов в открытом виде, `shutdown_all()` на остановке.
  `cargo check`/`cargo test` проходят.
- **A6 закрыта**: сервер-арбитр завершает ходы сквозняком. Финал проблемы —
  headless-циклу не хватало игрового frame loop'а GUI: серверная ветка
  `TeamTurnConcurrent` теперь делает `Remote_Synchronize()` +
  `while (!GameManager_ProcessTick(false)) { MouseEvent::ProcessInput(); }`
  (ровно как GUI у клиентов). Плюс: сервер не элиминирует пиров (барьеры и
  кадровая синхронизация только логируют и ждут — ядро A3), oldest-drop в
  очереди приёмника, idempotent-завершение барьеров для повторных вызовов
  раунда, append-режим rollover ai_log. Три подряд зелёных прогона: 4 хода,
  все «server saw end-of-turn» True, полные гистограммы пакетов на сервере
  (00/45/52/53/54) совпадают с клиентами, 0 десинков.

## 10. Смена архитектуры (2026-11-13): отказ от peer-to-peer lockstep

Практика P2P-пути (меш, десинк-рестарты, пассивные барьеры, зеркалирование настроек
клиентов) показала, что peer-to-peer lockstep не тянет эксплуатационные требования
(реконнект, спектаторы, валидация). **Принято решение: полный переход на
клиент-сервер** — единственный игровой авторитет это headless-сервер под Horizon,
топология «звезда», клиенты переделываются в зеркала (ввод на сервер, авторитетное
состояние обратно), десинк чинится снапшотом состояния, а не рестартом партии.

Актуальный план — `PLAN.md` (версия 2.0): фаза 1 (звезда + авторитет сервера),
фаза 2 (SNAP/DELTA + реконнект), фаза 3 (спектаторы), фаза 4 (полная валидация
приказов), фаза 5 (публичный сервер, метрики, CI). Разделы 1–9 этого документа
остаются как описание проделанной работы и как справочник по headless-движку,
лобби и сборкам.
