# r0-measure — измерения R0 (HD-ремастер)

Инструмент для гейта **R0** трека `max-brh-docs/development/remaster-hd.md`:
измеряет память рендера текущего 640×480, инвентарь ассетов с HD-объёмом
(×2/×4) и скорость транскодера KTX2 → RGBA8. Отчёт с числами —
`max-brh-docs/development/r0-measurements.md`.

Отдельный Cargo-проект (свой `Cargo.lock`), **не входит** в workspace `max-brh`
и не меняет прод-код: он только читает `MAX.RES`/`COLOR.PAL`/`*.WRL` через
`max_assets`/`max_render` и грузит рабочий набор через
`max_app::assets::Assets::load` (headless, без SDL и звука).

## Команды

```sh
cd max-brh-qa-tools/r0-measure

# 1. Память рендера текущего режима (heap-замеры + стоимость кадра при S=1/2/4)
cargo run --release -- vram --root ../..

# 2. Инвентарь ассетов и HD-объём (×1/×2/×4), с CSV
cargo run --release -- inventory --root ../.. --csv ../../build/r0-inventory.csv

# 3. Транскодер: basisu (pure Rust) vs ktx-rs (порт libktx) на реальной графике
cargo run --release -- transcode --root ../.. --iterations 30 --dump ../../build/r0-ktx2
```

`--root` — корень репозитория (каталог с `max-original/MAX.RES`); без него
ищется вверх от текущего каталога.

## Что и как измеряется

### `vram`

Три группы, чтобы числа не смешивались:

1. **кадровый путь** — `RgbaBuffer` 640×480 аллоцируется и замеряется
   трекинг-аллокатором (`src/alloc.rs`); текстура SDL и drawable считаются
   аналитически по точным вызовам `SdlWindow::present`
   (`create_texture_streaming(RGBA32, w, h)` и drawable у `Canvas`) — GPU
   headless не опросить, поэтому там формула, а не замер;
2. **рабочий набор** — `Assets::load` тем же вызовом, что делает клиент;
3. **изолированные компоненты** — спрайт-листы, terrain-атлас и библиотека
   UI-картинок декодируются повторно теми же функциями `max_assets`, поэтому
   их объём виден без доступа к приватным полям.

Дополнительно тот же кадр рисуется текущим (по-пиксельным CPU) рендерером при
`S ∈ {1,2,4}` в логический кадр `640·S × 480·S` с `zoom = 64·S` — это замер
стоимости кадра, а не оценка.

Замеры времени — медиана и минимум из 20 кадров (машина шумит).

### `inventory`

- Картинки классифицируются общим классификатором
  `max-resources-viewer::model::classify_archive` — те же классы, что у
  экспортёра PNG, поэтому инвентарь не расходится с `max-brh-assets/images/`.
- Тайлы берутся из всех 24 `*.WRL`; уникальность — по паре
  `(палитра карты, пиксели тайла)`: одинаковые индексы под разной палитрой
  дают разную текстуру.
- Шрифты — встроенные GNW-растры (`max_render::text::gnw`, 255 глифов × 3
  шрифта), те самые байты, которыми рисует рендерер.
- Объём: `байты = пиксели × S² × 4` (RGBA8, каждый исходный пиксель
  превращается в S×S).

### `transcode`

1. Тестовые картинки собираются из реальной графики: тайл 64×64, его ×4
   вариант 256×256, `FRAMEPIC` 640×480 (окно) и кадр `TANK` 44×45.
2. Кодируются in-process энкодером `ktx-rs` (порт KTX-Software) в ETC1S
   (BasisLZ) и UASTC LDR 4×4 — оба кодека, между которыми выбирает пайплайн.
3. Декодируются двумя рантайм-кандидатами; каждая итерация — весь путь
   загрузки (разбор контейнера + транскод), как его вызывает загрузчик ассетов.
4. Выход хешируется FNV-1a 64: хеши совпадают у обоих Rust-декодеров и у
   C-эталона (см. отчёт), поэтому «быстрее» не покупается ценой «другие
   пиксели».

`--dump DIR` сохраняет сгенерированные `.ktx2` — на них же гоняется C-эталон
(upstream `basisu_transcoder`, тот код, который встроен в libktx; харнесс
`build/r0-cbench/bench.cpp`, в репозиторий не входит).

## Воспроизводимость

- Все числа — из одного и того же `max-original/MAX.RES` (1828 записей) и
  24 `*.WRL`; версии крейтов зафиксированы в `Cargo.lock`.
- Замеры heap не зависят от раскладки структур: считаются фактические
  аллокации.
- Время: медиана N прогонов, N выбирается от числа пикселей
  (`--iterations` переопределяет). Абсолютные мс зависят от машины, отношения
  (×1:1, basisu/ktx-rs) устойчивы; в отчёте указано, на какой машине снято.
